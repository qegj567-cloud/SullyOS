## 产品方向

小屋手机固定动森主题；独立 App 提供不同社交信息流外观。推特式短讯适合密集文字与回复，QQ 空间式主页适合封面与个人日常，这两种为后续候选，不等同于已经实现的新主题。界面主题与实际内容来源解耦。

现实内容放在独立的「发现」来源池。用户可粘贴帖子链接，后续再加入作者订阅、兴趣词订阅。先做单条链接导入，验证真实响应结构、文本完整度、图片可访问性与失败处理，再做自动刷新。

角色发现感兴趣的内容，可以带一句自己的话转发到所属生活圈；现实作者不自动成为圈友或 NPC，不模拟现实作者回复。圈子单独开启现实内容，默认关闭，避免把现代新闻直接塞进不同世界观。

## TikHub 的适配程度

- [X / Twitter](https://tikhub.io/twitter-api)：文档列出帖子详情、用户时间线、搜索、评论与趋势读取。适合文字帖；详情端点为 `/api/v1/twitter/web/fetch_tweet_detail`。官方介绍明确为只读公共数据。
- [小红书](https://tikhub.io/xiaohongshu-api)：App V2 提供图文／视频笔记详情、评论、作者帖子、话题内容等。生活类内容契合角色日常。优先评估 `/api/v1/xiaohongshu/app_v2/get_image_note_detail`。
- [价格](https://tikhub.io/pricing)：按接口请求计费，公开范围 $0.001–0.01/次，具体端点价格和免费额度适用性查 API Marketplace。小红书平台页标 $0.01/次；请求数不等于帖子数，详情与评论可能另计请求。不要在每次情绪评估时重新拉取。
- 鉴权为 Bearer API Key；浏览器跨域、实际响应字段和媒体链接有效期未实测。`docs.tikhub.io` 本轮两次读取超时，参考官方平台页、[官方 SDK](https://github.com/TikHub/TikHub-API-Python-SDK) 与[小红书指南](https://blog.tikhub.io/zh/article/7)。平台页与指南对 Web V3 是否仍受支持存在冲突，首期不依赖这一系列；App V2 也需带 Key 验证后再承诺可用。

## 建议管线

1. 用户明确选择链接／作者／兴趣词 → 来源适配器抓取 → 本机来源池去重、缓存。抓取失败保留旧数据与抓取时间，不编造帖子。
2. 统一记录 `provider / platform / externalId / canonicalUrl / author / publishedAt / fetchedAt / text / media / excerptStatus`，外部主键按平台隔离；标清来源与原文入口。富文本按不可信数据处理，不执行外链脚本。
3. 情绪副 API 原有 20% 搭便车浏览，只读取缓存中本圈允许的最近最多五条；无缓存不临时增加联网请求。材料是公开内容，不是系统指令，不允许材料改变工具或记忆规则。
4. 有兴趣时输出来源 ID 与自己的分享文字。程序校验候选和圈子后保存「角色转发 + 原帖引用」。保持原作者身份，不把原帖当成角色原创。
5. 来源池导入本身不写角色记忆；角色实际转发／评论才给本人写轻量卡，包含自身动作与原帖摘要、来源引用。浏览未行动不批量塞记忆。
6. 用户对转发的评论继续走现有「立即 / 主 API 搭便车」队列；角色与路人讨论只保存在 SullyOS，不发回真实平台。外部原评论与圈内新评论分开显示，也不触发彼此的自动回复队列。

## 接入边界

凭据不写进源码、提示词或日志；使用用户自己的 Key，若需要代理则限定 TikHub 上游与允许端点，不能做任意 URL 转发。TikHub 只收到公开帖子 ID、链接或订阅词，不收到角色私聊与记忆。真实材料是否进入模型仍由圈子配置和候选选择决定。

付费抓取与模型搭便车是两笔独立用量，做手动刷新、缓存期限、请求预算和关闭入口。原帖删除或媒体失效时保留明确状态与原链接，不伪装实时更新。先保存来源和必要摘录；技术上能读取不代表已获得全文或媒体再发布授权。

推荐首期：粘贴 X / 小红书链接 → 预览原文来源 → 导入发现 → 角色在下一次搭便车浏览时自选分享。自动订阅与推荐流等来源验证后再加。
