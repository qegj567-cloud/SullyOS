# 备份与恢复：内存有界的链路

改备份导出、恢复、云端上传下载、备份格式，往数据库里加新表，或者新增 localStorage 键之前，先读这一份。

这是一份改造方案：「现状」一节记录当前代码的实际行为，其余各节是目标设计和落地顺序。某一期落地后，把对应小节从「目标」改写成「现在这样」。

## 目标

备份多大，不应该影响能不能备份、能不能恢复，只影响花多久、占多少磁盘。下面六条规则是整套设计要守住的东西，后面每一节都在回答「怎么守住它们」：

1. **整份备份只以磁盘文件的形式存在。** 导出直接写进本地临时文件（OPFS，浏览器给每个网站的私有文件区）；云端下载也先落到临时文件；用户自己选的备份文件本来就在磁盘上。内存里任何时候都不出现一整份备份。
2. **任何环节内存里只放「一片」。** 一片是一页数据库记录（按字节封页，约 4MB；单条记录超过上限时独占一页），或者一个二进制项。只有两类东西允许超出一片，而且必须写明量级：
   - 单个二进制项本身，比如用户存进来的一张图、一个模型包。写进 IndexedDB 时它必须是一个完整的 Blob。
   - 和条目数成正比的目录信息，包括清单、压缩包目录、引用集合。每个条目几百字节到 1KB，靠按字节封页把条目数压住。
3. **读备份只按需读。** 先读压缩包末尾的目录，再按字节范围读用得到的那一项，不整包读入。
4. **恢复逐页写库。** 每张表清空一次，再一页一页写进去，不先把全部数据拼在内存里。
5. **所有传输都是「分片文件 + 最后写的完成清单」。** GitHub 和 WebDAV 共用一个上传器，只是底层传输不同。上传成功以远端实际大小为准，不以状态码为准；下载要核对每片的摘要。
6. **备份范围必须登记。**
   - 数据库表：没登记的默认带上，因为漏带就是丢数据。
   - 本地设置（localStorage）：没登记的默认不带，因为多带会带走凭据和这台设备自己的状态。
   - 两张分类表都由测试保证没有漏登记。

## 现状

这一节记录改造开始时的状况，是后面各期要解决的问题清单。哪一条在哪一期解决、现在做到哪一步，见「分期落地」。

### 整份数据在内存里的位置

| 环节 | 整块留在内存里的东西 | 位置 |
|---|---|---|
| 导出暂存 | 所有条目（分片 JSON、图片、语音）都以 Blob 形式存到最后才压缩 | `utils/backupArchive.ts:11-18` |
| 导出输出 | 整个压缩包，由 1MB 的 Blob 片段拼成 | `utils/backupArchive.ts:58-94` |
| 记忆向量 | 全部向量拼成一个 `Uint8Array` | `utils/memoryPalace/db.ts:318` |
| 多空间导出 | 每页按条数（100 条）封页，不看字节；角色表整表 `getAll`；每个素材都整个读一遍算哈希 | `utils/userSpaceBackup.ts:99,113` |
| 打开备份 | JSZip 把整个文件读成一个 ArrayBuffer | `context/OSContext.tsx:4428` |
| 单空间恢复 | 所有表拼成一个完整的数据对象后才写库 | `utils/backupFormat.ts:327-353` |
| 多空间恢复 | 所有空间的所有行、所有共享图片读进内存校验完才写库 | `utils/userSpaceBackup.ts:223-273` |
| GitHub 下载 | 各分片的 ArrayBuffer 先存成数组，再拼成 Blob | `utils/githubClient.ts:1014-1033` |
| WebDAV 下载 | 8MB 一段，各段先存成数组再拼成 Blob；分段失败时退回整包下载 | `utils/webdavClient.ts:279-340` |
| WebDAV 原生上传 | `blob.arrayBuffer()` 读入整包 | `utils/webdavClient.ts:96` |

数据库读取本身已经是逐条或逐页的，JS 堆里只有几 MB。整份数据堆在上表这些「最后一步」和「第一步」里。

Blob 是否真的占内存，取决于浏览器引擎，而且两家的行为都不可控：

- Chromium 会把超过内存额度的 Blob 挪到磁盘，安卓上的额度约为手机内存的 1%。
- WebKit 先把 Blob 数据放在网络进程的内存里，再在后台写到临时文件。单个大 Blob 能让这个进程被系统杀掉。上传一个在内存里拼出来的 Blob，还要再完整复制一份。

依赖引擎自己把数据挪到磁盘，没有确定性，这是规则 1 存在的原因。

### 结构和正确性问题

- **两套格式，两套读写代码。**
  - 单空间格式：`manifest.json` 加 `stores/`、`blobs/`。导出按字段手写（`context/OSContext.tsx:3565-4340`），恢复靠 `DB.importFullData` 逐个字段处理。
  - 多空间格式：`user-spaces.json` 加 `spaces/`、`shared/`，按数据库里实际的表枚举（`utils/userSpaceBackup.ts`）。
  - 只有一个空间时走前者，有多个空间时走后者。
- **「备份哪些表」散落在至少六处：**
  - `OSContext.tsx` 里的 `allStores`、仅媒体子集、`noImageStores`、`backupArrayFieldByStore`；
  - `db.ts` 里 `importFullData` 的 `availableStores`；
  - `userSpaceBackup.ts` 里的 `mediaStores` 和排除规则；
  - `legacyIndependentUserImport.ts` 里的 `tableFields`。
- **手写清单已经漏了表。** `xhs_owned_posts` 不在单空间导出清单里，但恢复端认识它（`db.ts:4404`），所以单空间备份从来没带过这张表。
- **多空间导出带走了不该带的设置。** 它带走所有共享设置键（`userSpaceBackup.ts:133-139`），其中包括主动消息的待发凭据、凭据指纹、时钟水位、推送令牌（`userSpaces.ts:56-74`），恢复时也会无条件写回。迁入独立用户的逻辑早就把这类键排除在外（`independentUserImport.ts:9-10`），说明它们属于原来那台设备。
- **原生壳的 WebDAV 上传在传垃圾数据。** 上传时把 ArrayBuffer 直接交给 CapacitorHttp。Android 上已从 Capacitor 源码确认：传上去的是 2 字节的 `{}`，服务端照样回 201（原因见「平台事实」）。iOS 原生实现不在仓库依赖里，没有核对。再加上只认状态码、只保留 5 份，几次这样的上传就能把好备份全部挤掉。
- **WebDAV 清理会删掉刚传完的备份。** 列表按文件名倒序排，而文件名是 `Sully_Backup_<模式>_<时间戳>.zip`，实际是先按模式排：仅文字永远排在全量前面。云端已有 5 份仅文字备份时再传一份全量，上传成功后清理只留前 5 份，刚传的全量被删。
- **网页端 WebDAV 上传有 100MB 硬上限。** 它要经过 Cloudflare Worker 代理，超过上限直接拒绝（`webdavClient.ts:26,217-223`）。
- **WebDAV 上传只认状态码**（`webdavClient.ts:190`），清理旧备份时也不区分坏文件（`:390-407`）。
- **GitHub 下载只核对分片大小**（`githubClient.ts:971`），没有用到清单里记录的摘要。
- **「上次备份时间」打包完就记上了。** 两处都在 `exportSystem` 里面（`OSContext.tsx:3581,4327`）。云备份上传失败也算备份过，备份提醒会因此一整个周期不出现。
- **导入中断提示：** 校验失败、数据库一行没写，也会留下提示；点「稍后再说」后，下次启动照样再弹（`PhoneShell.tsx:1215-1217`）。

## 目标架构

```
导出：数据库 / 本地设置 ──按字节封页读──▶ 归档写入器 ──顺序压缩──▶ 临时文件（OPFS）
                                                                 │
                       本地保存（用户点「保存」） ◀───────────────┤
                       GitHub / WebDAV：分片 + 完成清单 ◀─────────┘（都从临时文件切片）

恢复：用户选的文件 / 云端下载落盘的临时文件 ──按需读──▶ 归档读取器 ──逐页──▶ 写库
```

### 一种格式

所有导出统一产出多空间格式（`sully-user-spaces`），只有一个空间的用户也导出这种格式，范围是当前空间。单空间的三代旧格式（`data.json`，以及 `manifest.json` 的二代、三代）只保留读取，不再产出。

选多空间格式的理由：

- 它已经按数据库里实际的表来枚举；
- 图片按内容哈希只存一份；
- 记录本身就是分页存的；
- 多空间用户已经在线上用着它。

统一时这套格式升到 `version 2`，一次定下以后不再动的布局：

- **按字节封页。** 每页约 4MB，单条超过上限时独占一页。现在按 100 条封页，100 条带内联旧图的消息就可能有几百 MB。
- **图片类二进制（Blob）进 `shared/<sha256>.bin`**，按内容去重。哈希直接用共享图片池里已有的内容编号（`utils/sharedBlobPool.ts:5`，`pool_<sha256>`），不再为算哈希把每个素材整个读一遍。
- **其余二进制（向量的类型数组、ArrayBuffer）按页打包进同一页的 `.bin`**，页内记偏移。现在这类值是一个值一个压缩包条目，上万条向量就是上万个条目。
- **读取端**：认 `version 1` 和 `2`。遇到更高的版本，提示「这份备份来自更新的版本，请先更新」，不能笼统地报「格式无效」。

代价：还没更新的客户端（旧版原生壳、旧的二改部署）读不了新备份。

**退役单空间导出之前，下面每一条都要有结论：**

| 单空间路径现在做的事 | 统一后 |
|---|---|
| 导入后对账主动消息云端：取消孤儿任务、清掉云端已不存在的角色、置对账标记（`OSContext.tsx:4970` 一带） | 多空间恢复导完直接刷新（`:4429-4440`），没有这一步。必须补上，否则云端会继续给已不存在的角色发消息、继续消耗额度 |
| 导入前拒绝不支持的老结构（`assertSupportedSullyBackup`，`:4478`）、SAR 重置、本地设置镜像快照 | 逐项确认在统一路径里有没有对应的处理 |
| 本地设置按白名单逐项带 | 通用格式带走全部共享键。改成分类表登记，默认不带（见下文） |
| 恢复进当前空间 | 按备份里记录的空间编号恢复，确认框写明会覆盖哪个用户，或会新建哪个用户（理由见「取舍」第 9 条）。想另起一个用户，用「迁入为新用户」 |
| 仅文字模式：剥掉图片，通话截图标记为过期 | 确认通用导出怎么处理行内的旧 base64 图片，缺的补上 |
| 仅媒体模式：角色只导出媒体字段，恢复时贴回本机已有的角色 | 已有 `spaceMediaRow`，恢复时合并进已有行 |
| 主题、表情、表情分类、手帐贴纸、角色分组：恢复时与本机合并 | 改为整表替换：恢复后和备份一致，本机多出来的条目不保留 |
| `vr_settings`、`vr_scripts`、`vr_plays`、`vr_presets`：逐条写入，不清空 | 同上，整表替换 |
| 导出时遇到解不开的旧 base64 图片：跳过它、提示跳过了几处，并写一份诊断（`diagnostics/malformed-images.json`），记录每张坏图属于哪条记录、哪个字段、坏在哪里 | 跳过和提示照旧。诊断并进已有的缺失素材清单（`diagnostics/missing-assets.json` 和 `缺失素材清单.txt`），每条注明是「缺失」还是「损坏」。这样只保留一套排查清单 |
| 主题、API 配置等运行时状态 | 带空间本地设置的原值，恢复后刷新页面 |
| 是否带走后端连接（备份偏好） | 已支持，但只覆盖 `backend` 字段。共享设置里的主动消息键同样要受这道门控制，由本地设置分类表统一处理 |
| 协同工作独立库 | 按 `collab_` 前缀枚举 |

### 写入：顺序写进临时文件

- **归档写入器**改成「打开 → 一项一项顺序加入（每项写完再加下一项）→ 关闭」。每一项交给 zip.js 后立刻释放，不再攒到最后。文字先编码成字节再加入（原因见「平台事实」里 JSZip 那条）。
- **输出**直接写进 OPFS 文件的可写流。zip.js 每写一块都会等这块写完，再接收下一块。前提是条目顺序加入：并发加入，或者开启缓冲写入，都会让 zip.js 走一个没有上限的缓冲区。
- **数据库读取**每页一个独立的只读事务：游标逐条读，累计到字节预算或条数上限就关掉这个事务，异步写进归档，再从上一页最后一个主键继续读。角色表也这样分页读。代价见「取舍」第 1 条。
- **图片**从图片库读出的 Blob，直接作为数据源交给 zip.js，不读成 ArrayBuffer。
- **降级**：
  - 只在开始前决定写到哪里。浏览器不支持在页面里写 OPFS 文件（iOS 26 以前），或者开始前就发现配额不够，就写进内存里的 Blob 片段。
  - 走这条退回路径时，行为和现在完全一样，不额外拒绝（理由见「取舍」第 10 条）。
  - 估算体积超过 500MB 时提示一句：「系统版本较旧，备份较大时可能失败，建议升级系统或在电脑上导出」。500MB 是起始值，有真机数据后再调整。
  - 写到一半出错（比如配额满了），就整次失败、删掉临时文件、说明原因，不中途改成写内存。

### 读取：按需读

- **所有备份读取**统一用 zip.js 的 `ZipReader` 配合文件读取器：先读末尾目录，再按字节范围读条目。打开 `checkSignature`，每个条目的 CRC 校验等于白送。
- **读取适配层**（`utils/backupZipReader.ts`）的接口和 JSZip 的读法同形，行为也向 JSZip 对齐：文件名编码、路径归一、包尾多余数据、被切开的 emoji（见「平台事实」）。读文字时边解压边解码，不先攒出一整块 Blob。读文件失败和内存不足的错误原样抛出，不报成「备份损坏」。
- **旧格式读取和多空间读取**都通过一层「按名字取条目」的小适配改用它，读取逻辑本身不动。
- **交给 `ZipReader` 的必须是文件或 Blob，不能是流。** zip.js 文档写明，传入流时会把整个流缓冲进内存。项目里已有先例：`utils/live2dModelStore.ts` 用 `ZipReader` 按需读模型包。
- **旧格式按字段懒加载**（`utils/backupFormat.ts` 的 `openLegacyBackup`）：
  - 打开备份后，清单里每个有分片的字段先是一个占位。占位能回答「有没有这个字段」「有多少条」，这些答案都来自清单，不用读数据；读它的内容会直接报错，所以漏接的使用点会当场暴露，不会被当成空表去清库。
  - `importFullData` 本来就逐段处理、处理完就把这段置空。现在轮到某一段时才把它的分片读进来，并且先读到手、再清那张表。恢复峰值从「全部文字数据」降到「最大的一张表」。
  - 打开时会把每个字段完整读一遍、验完就丢：分片齐全、CRC、能解析、条数对得上。这样文字数据的损坏仍然在写库前被拒绝，代价是每个分片读两遍。
  - 例外，同一时刻不止一个字段在内存里：
    - 整合备份的角色和媒体字段要一起合并；
    - `importFullData` 不经手的字段（协同工作的三张表、几个设置数组）在各表写完之后一起读入，其中协同工作三张表要在一个事务里写；
    - 仅媒体的旧包在开头会临时读一遍素材表。
  - v1 的 `data.json` 是单个 JSON，拆不开，仍然整个读入。「迁入为新用户」要整份数据同时在手，峰值也没有变，留给第二期。
  - 文件在恢复过程中要一直读得到。写库中途文件被移走或被系统收回读权限，这次恢复就会中途失败，需要重新导入。
- **损坏的处理分两类**：
  - 文字数据（清单、各表分片）损坏，在写库前整体拒绝，数据库不变。
  - 单张图片的二进制损坏（旧格式的 `blobs/*` 和 `assets/*`，多空间格式的 `shared/*.bin` 和行内图片），跳过这一张，其余照常恢复。一张坏图不该挡住全部聊天记录的恢复。
  - 被跳过的图片先记在本机，页面照常刷新，重启后再提示。写完库之后页面还带着恢复前的内存状态，停在那里等用户确认的话，后台的自动保存可能把旧状态写回刚恢复的库。
  - 一次恢复里第一次遇到坏图时，回头重读一次清单确认备份文件本身还读得到；读不到就按文件失效中止，不再继续跳过。
  - 其余二进制（收藏语音、协同工作附件、记忆向量）损坏，仍然在写库前整体拒绝：它们没有「空着」的表示法。索引里有、包里却没有的图片也仍然整体拒绝。
  - 读文件失败和内存不足不算损坏，一律中止并报错，否则「文件被系统收回」会被当成几千张图损坏，然后继续往下清表。读取适配层按排除法判断：这两类错误原样抛出，其余都算损坏（`BackupCorruptError`）。iOS 上文件被收回时实际抛什么类型，要在真机上确认。

### 恢复：逐页写库

顺序固定，每一步都只用有界的内存：

1. **整体检查。** 检查格式和版本，确认清单列出的每个条目都存在，模式合法；读角色那几页，只取角色编号，检查有没有和别的空间冲突。不通过就整体拒绝，数据库不动。
2. **「迁入为新用户」多扫一遍。** 先逐页扫角色、记忆节点、向量，只建「旧编号 → 新编号」的映射，映射只含编号。之后的写入阶段边写边改编号。
3. **共享图片先写，只增不覆盖。** 逐个读、逐个写。内容哈希冲突就在这一步暴露，还没动任何表。
4. **逐空间、逐表写入。** 替换模式下：清空这张表，同时把本机专属、导出时被过滤掉的行补回去（`assets` 表的 `ls_mirror_v1`、`user_spaces_catalog_v1`，见 `userSpaceBackup.ts:117`）。清空和补回放在同一个事务里，然后逐页读取 → 解包 → 用一个事务写一页 → 释放。
5. **行级校验在写那一页时做。** 行内引用的共享图片如果在包里不存在，按缺图处理：警告并跳过，和现有缺图规则一致。其他校验失败就停下，提示重新导入。

中途失败或者页面崩溃时，已经写过的表是新数据，还没写到的表仍是旧数据。导入本来就以「备份覆盖本机」为前提，可以重新导入，所以不做回滚，也不记日志。底线是不让人卡进反复崩溃的循环：只有真正开始写库后才写「导入中」标记，并提示重新导入。「迁入为新用户」沿用现在的清理：失败时删掉这次新建的空间。

### 传输：一个上传器，两种底层传输

- **上传**：从临时文件按 32MB 切片，每片作为一个远端文件上传，最后上传完成清单。清单里记录每一片的名字、大小和 sha256。GitHub 现在就是这套做法；WebDAV 改成同一套之后：
  - 不再受代理 100MB 上限的限制；
  - 原生壳也不需要整包进内存。
  - 每一片传的是 `file.slice(...)`，不是原文件对象，原因见「平台事实」里的 WebKit 319985。原生壳传二进制时按 GitHub 现有的做法转成 base64，并加上 `dataType: 'file'`。
- **核对**：每片上传后读取远端大小，对不上就重传，三次失败就删掉这次已传的分片并报失败。没有完成清单的一组分片，不算一份备份。
- **下载**：每一片直接写进临时文件，并核对大小和摘要（`utils/backupDownload.ts`，GitHub 和 WebDAV 共用）。
  - 写磁盘还是写内存只在开始前决定，中途不切换；下一片要等上一片写完才取，所以内存里同时只有一片。
  - GitHub 用资源对象上的 `digest`（sha256）核对每一片，对不上就重拉这一片；没有摘要时只核对大小。
  - WebDAV 网页端按流写入；服务器报了大小就核对总字节数。分段下载只认 206，服务器回 200 说明它没理会分段请求，改为整包按流下载。
  - 下载结果用完要显式释放，临时文件随之删除。
- **列表与清理**：WebDAV 列表按完成清单把分片归成一份备份。旧的单文件备份照常列出、照常可以恢复。清理旧备份只在本次上传核对通过后进行，不完整的那组分片不计入保留份数。
- **「上次备份时间」**：本地导出在保存成功后记，云备份在核对通过后记。

### 本地保存

- 浏览器的分享面板（`navigator.share`）需要用户刚刚点过屏幕才能调起。导出要好几分钟，导完时这个条件早就失效了。所以导出完成后显示一个「保存」按钮，由用户点击触发分享或下载。
- `<a download>` 下载没有完成信号，点了下载不能马上删掉临时文件。临时文件留到下一次备份开始时、或者过期清理时再删。

### 备份范围：两张分类表加覆盖测试

- **数据库表分类表**登记主库和协同库里的每一张表：怎么备份（全量；仅媒体时保留哪些字段；仅文字时怎么处理），或者为什么不备份（例如 `blob_assets` 走共享图片，`api_call_log` 是本机调用记录）。
  - 导出遍历数据库里实际存在的表，查这张表决定怎么处理。遇到没登记的表，照常全量备份并打警告。
  - 测试从建表定义里取出所有表名，断言每一张都已登记。
- **本地设置分类表**登记每一个要带走的键，或者带走规则（前缀、正则），并标出它属于哪一类：
  - 普通设置：随备份走；
  - 凭据：受「带走后端连接」偏好控制；
  - 设备状态：推送令牌、待发凭据、时钟水位、导入进度等，永远不带；
  - 隐私：定位等，永远不带。
  - 没登记的键默认不带。
  - 这次改造新增的本机状态键 `sullyos_notice_restore_damaged_assets_v1`（恢复时跳过的坏图清单，重启后提示一次就清掉）属于设备状态。
  - 测试枚举代码里出现过的 localStorage 键名（常量和前缀），断言每一个都能归到某一类。

### 临时文件

实现在 `utils/backupTempFile.ts`。

- 放在 OPFS 的 `backup-tmp/` 目录，文件名带上用途和时间。
- **用着就一直持锁，没锁的就是垃圾。** 每个临时文件从创建起持有一把同名的 Web Lock，直到被删除；页面关闭、刷新或崩溃时，浏览器自动放锁。创建时先拿锁、再建文件，所以别的标签页的清理不会删到正在建的文件。
- **启动时删掉所有拿得到锁的残留**，不设保留期限。崩溃留下的大文件如果继续占着配额，下一次导出预判空间不够就会退回内存写入，正好落在最容易崩的设备上。
- **重试只在页面内进行。** 上传失败后，同一个页面拿着同一个文件重传；刷新之后文件会被当成残留清掉，需要重新导出。
- 保存、恢复、上传结束后删除。`<a download>` 触发的下载没有完成信号，文件留到下一次备份开始或页面关闭。
- **能力探测真写一个小文件**，并且要求有 Web Locks；任何一步失败都算不可用，走内存降级。结果在页面生命周期内只探测一次。只看接口在不在是不够的：有的 WebView 里 `createWritable` 存在，但一调用就报错。
- 开始前用 `navigator.storage.estimate()` 估算空间。它给的是配额减去已用量，不是磁盘真正剩余的空间，所以只能用来预判；写的过程中报配额不足，就按「写到一半出错」处理。
- 调用方写完必须先关闭写入流，再取文件；不关流，OPFS 不会提交内容。
- 导出、恢复和上传的长任务期间申请屏幕常亮（Screen Wake Lock），避免锁屏后页面被挂起。页面切到后台时系统会收回它，回到前台时重新申请。

### 并发

- 导出从读库到压缩结束，全程持有共享素材锁的共享租约（`utils/sharedAssetLock.ts`，多空间导出现在已经这样做）。删图、一键优化、导入持有独占租约，彼此等待。上传阶段只读临时文件，不持锁。
- 记忆整理这类「删旧插新」的后台重写，在导出租约存在期间延后执行，避免一行在按页读的过程中被搬到已经读过的位置（见「取舍」第 1 条）。
- 页面刷新（网页更新、切换空间）会打断备份。数据不受影响，残留的临时文件由启动清理收掉。

## 平台事实

以下核对于 2026-11。动手前，对标了版本号的条目再查一次。

- **Chromium Blob**：超过内存额度就挪到磁盘。桌面 x64 的额度是 2GB，安卓是总内存的 1%；磁盘额度安卓 6%、桌面 10%。短时间内大量创建 Blob，可能在挪走之前就撑爆渲染进程。来源：[Chromium blob README](https://chromium.googlesource.com/chromium/src/+/main/storage/browser/blob/README.md)。
- **WebKit Blob**：数据先放在网络进程内存里，后台再写到临时文件并做内存映射，单个大 Blob 仍可能让这个进程被系统杀掉。来源：[WebKit PR 3448](https://github.com/WebKit/WebKit/pull/3448)。上传请求里，内存里的数据段会被复制进请求体，文件段保持文件引用（WebKit `FormData.cpp`）。
- **OPFS**：
  - Safari 15.2 起支持 `getFile()` 和 Worker 里的同步写法；Safari 26.0 起支持在页面里用 `createWritable()` 直接写（[MDN 兼容数据](https://github.com/mdn/browser-compat-data/blob/main/api/FileSystemFileHandle.json)、[Safari 26 发布说明](https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes)）。
  - 配额：浏览器里每个网站最多可用磁盘的 60%；加到主屏幕的网页应用和 Safari 一样；其他 WebKit 应用（包括原生壳）每个网站 15%（[WebKit 存储策略](https://webkit.org/blog/14403/updates-to-storage-policy/)）。
- **WebKit 319985**：在 iOS / macOS Safari 26.5 到 27.x 上，把一个落在磁盘上的 File（文件选择器选来的、从 IndexedDB 读回的、从文件 App 拖进来的）直接交给 XHR 或 fetch 上传，实际发出去的是 0 字节，页面这边没有任何报错。
  - 修复 2026-10-10 合入主干，并挑进了 safari-7626 分支（[bug 319985](https://bugs.webkit.org/show_bug.cgi?id=319985)）。
  - 绕法：上传前做一次 `slice()`，不复制数据。
  - 报告里列出的受影响来源不包括 OPFS 文件，但 OPFS 文件属于同一类，必须在真机上验证。
  - 页面没法检测自己是否受影响，所以这个绕法一直保留。
  - 本项目的 `sw-keep-alive` 会接管所有页面（`clients.claim()`），正好符合最早那份报告里的触发条件。
- **CapacitorHttp 传二进制**：直接调用 `CapacitorHttp.request` 时，参数经 `JSON.stringify` 交给原生层，ArrayBuffer 会变成 `{}`。Android 原生层在请求既不是 JSON、也没标 `dataType: 'file'` 时，把这段文字原样写进请求体（`@capacitor/android` 6.2.1 的 `CapacitorHttpUrlConnection.setRequestBody`）。所以二进制必须转成 base64 并标上 `dataType: 'file'`。Android 8 以下不解码 base64，会写出空请求体，靠上传后的大小核对拦下。iOS 原生实现不在本仓库依赖里，没有核对。
- **流式请求体**（边生成边上传）：Chrome 要求 HTTP/2 和 `duplex: 'half'`；Safari 到 27.3 beta 才支持（[Safari 27.3 发布说明](https://developer.apple.com/documentation/safari-release-notes/safari-27_3-release-notes)）。本方案不依赖它。
- **zip.js**：
  - `ZipReader` 接到 Blob 或 File 时按需读，接到流时把整个流缓冲进内存（[ZipReader 文档](https://github.com/gildas-lormeau/zip.js/blob/master/docs/classes/ZipReader.md)）。
  - `ZipWriter` 遵守可写流的背压，前提是条目顺序加入。
  - 只有压缩级别 6 才走浏览器原生的压缩接口。
  - `checkSignature` 默认关闭。
  - 文件名没有 UTF-8 标志位、也没有 Unicode 路径扩展字段时，默认按 CP437 解码；JSZip 按 UTF-8 解码。读取时要显式指定 UTF-8。
  - 不做路径归一。JSZip 读包时会去掉 `./` 和空路径段，读取适配层照做，否则二次打包过的备份会找不到条目。
  - 末尾目录之后的多余数据默认最多容忍 64KB，JSZip 不限。读取适配层放宽到 1MB：正常的包读取量不变，只有包尾确实有多余数据时才多读这一段。不开宽松模式，它找不到末尾目录时会扫描整个文件。
  - 每次读条目都按自己的偏移新建读取流，没有共享游标，可以并发读；`close()` 在 2.8.43 里是空操作。
  - 仓库当前装的是 2.8.43。
- **JSZip 写入字符串时会把跨块的 emoji 写成两半。** 它把字符串按 16K 个码元切块，每块单独做 UTF-8 编码。一个 emoji（代理对）正好跨在块边界上时，浏览器里写出来的是两个各 3 字节的代理半（形如 `ED A0 BD` 加 `ED B8 80`），不是标准的 4 字节序列。JSZip 自己的读取端很宽松，能把两半拼回去，所以用 JSZip 读没有问题；标准的 `TextDecoder` 会把它解成 6 个替换字符。现存的备份都可能带有这种写法，所以：
  - 读取端解码文字之前，先把成对的代理半换回标准的 4 字节序列（`utils/backupZipReader.ts`）；
  - 新的写入器先用 `TextEncoder` 把文字编码成字节，再交给压缩库，不再产生这种写法。

## 取舍

1. **按页读，不做整表快照。** 想要整表快照只有两条路：一是把整张表留在内存或 Blob 里，违反规则 2；二是让只读事务跨过异步写盘，但事务一回到事件循环就会自动提交，做不到。按页读的代价：
   - 导出期间被改动的行，备份里可能是改之前的版本，也可能是改之后的；
   - 「删旧插新、新主键更小」的写入，可能让这一行在备份里缺席。现实中这类写入来自记忆整理这样的后台重写，所以让它们在导出期间让路。

   多空间导出现在就是按页读，并且已经在线上运行。现在的备份本来也不是全库快照：主动消息、记忆整理在导出期间照样写库。
2. **不为全库一致冻结整个 App。** 那需要一个覆盖所有表的只读事务，期间所有写入都要排队，换来的跨表一致，恢复端并不依赖。
3. **不用流式请求体上传。** 主力用户的 Safari 正式版还不支持，Chrome 也有 HTTP/2 的限制。先写临时文件再切片上传，所有平台都能用。
4. **这次不做增量云备份。** 增量能大幅减少上传量，但云端要自己管理「哪些图片还被某份备份引用」，恢复时要拉很多小文件，GitHub 的附件数量和接口频率也有限制，本地导出更用不上。统一后的格式本身已经按内容哈希存图，以后要做也不必再改格式。
5. **备份引擎这次不搬进 Web Worker。** 搬过去要先剥离对 localStorage、空间目录这类主线程能力的依赖。iOS 26 起，页面里已经能直接写 OPFS。搬进 Worker 的收益主要是界面不卡，留到做后台备份时再评估。
6. **旧格式读取只做两件事：** 按需读包、按字段懒加载，组装和写库逻辑不动。现存的备份全是旧格式，这两件事让旧备份恢复的峰值从「整个压缩包 + 全部文字」降到「最大的一张表」。
7. **恢复不回滚。** 理由见「恢复：逐页写库」。
8. **表默认带上，本地设置默认不带。** 两者错误的代价不对称。漏带一张表就是丢用户数据。多带一个设置键，会把凭据或这台设备的状态（推送令牌、时钟水位）带到别的设备上，造成凭据泄露或者主动消息错乱。
9. **恢复按备份里记录的空间编号进行，不强行恢复进当前空间。** 「空间」就是用户空间：每个用户有一套独立的数据库，系统设置共用（见 [`docs/user-spaces.md`](./user-spaces.md)）。大多数人只有一个默认空间，按编号恢复和恢复进当前空间没有区别。区别只出现在本机有多个空间的时候。角色编号在所有空间里全局唯一，如果把一份空间 A 的备份强行恢复进空间 B，而 A 还在本机，两边的角色就会撞编号。按编号恢复就不会出现这种情况；想把备份作为一个独立的新用户导入，有现成的「迁入为新用户」。
10. **降级路径不设硬性拒绝。** 退回内存写入的设备（iOS 26 以前，或者配额不够），本来就在用现在这套做法。如果改造后反而拒绝它们做大备份，这部分人就会比现在更差。所以只提示风险，不拦。
11. **文字数据和记忆向量的校验是硬门槛。** 改用 zip.js 并打开校验之后，任何一个文字分片或向量文件校验不符，整份备份在写库前被拒绝。JSZip 不校验，向量文件里坏一个字节只会让某条向量略有偏差，照样恢复。保持严格的理由：做法简单，不把已知损坏的数据写进库。代价：手里唯一一份备份有轻微损坏的人，从能恢复变成不能恢复。单张图片损坏不在此列，见「读取：按需读」。

## 分期落地

每一期单独可发，发完都比上一期安全，并且不让任何一类用户的内存或正确性变差。测试要能在旧行为下挂、在新行为下过。

### 第零期：止血与探明

代码已完成，真机探明项待跑。

- **原生壳 WebDAV 上传**：二进制转成 base64 并标上 `dataType: 'file'`，和 GitHub 的做法一致。
- **WebDAV 上传后核对远端大小**：
  - 网页端用 PROPFIND 读大小；原生壳先直连发 HEAD，读不到再退回 PROPFIND，这样 Worker 够不着的内网服务器也能核对。
  - 读不到时重试 3 次。
  - 大小一致算成功；不一致算失败，并删掉这次传上去的文件；文件在但服务器不报大小，算成功，因为这类服务器无从核对，行为要和改造前一致；连文件在不在都确认不了，算失败，不删文件。
- **WebDAV 列表和清理按文件名里的时间戳排序。** 清理只处理本应用命名的备份文件；目录里其他名字的 zip 不占保留名额，也不删。服务器明确报了大小、而且小于 22 字节（zip 结尾目录记录的最小长度）的文件同样不占名额、不删：它不可能是一份备份，但只是推断出来的，不做删除。
- **单空间导出补上 `xhs_owned_posts`。**
- **「上次备份时间」**：本地导出在分享成功或触发下载后记，云备份在上传返回成功后记；同一次导出只记一次。
- **「导入中」标记**：全部只读校验通过、第一次写库（包括写图片库）之前才写。「迁入为新用户」失败、并且新建的空间已经清理干净时，清掉标记，因为这时本机数据没有变化。
- **探明**：Capacitor（`capacitor://` 协议）下 OPFS 能不能用；iOS 真机上传 OPFS 文件的切片，会不会受 319985 影响。入口是调试面板里的「OPFS 探针」（见 [`dev-debug.md`](./dev-debug.md)），结果写回本文档的「平台事实」。
- **测试**：除探明项以外，每一项都有回归测试。

### 第一期：临时文件模块与按需读包（不改格式）

代码已完成，真机验收待做。

- **临时文件模块**（`utils/backupTempFile.ts`）：Web Lock、启动清理、配额预判、出错收场、屏幕常亮。
- **zip.js 读取适配层**（`utils/backupZipReader.ts`），打开 `checkSignature`，`importSystem` 和 `importUserSpaces` 都经它读包。
- **云端下载写进临时文件**（`utils/backupDownload.ts`），并核对每片的大小和摘要。
- **旧格式按字段懒加载。**
- **测试**：
  - 用一个统计读取字节数的假读取器，打开大包只读一项时，读到的字节数约等于这一项的大小；
  - 三代旧格式的样例备份都能完整恢复，懒加载和一次读全写出的库逐表相等；
  - 懒加载后，同时在内存里的字段不超过一个；
  - 被锁住的临时文件不会被清理；
  - 浏览器里写出的、emoji 被切开的包，读出的文字和原文一致。
- **真机验收**（单元测试替代不了）：
  - iPhone（iOS 26 以上）从云端恢复全流程：下载落盘、按需读、恢复、临时文件被删。GitHub 和 WebDAV 各一次。
  - iPhone 从文件 App 恢复一份 1GB 以上的旧格式备份，不崩。位于 iCloud 或第三方云盘的文件单独试，确认恢复过程中一直读得到。
  - 恢复中途让文件失效（删掉源文件、长时间切后台），看 WebKit 实际抛什么错误，还是不报错而返回短数据。
  - iOS 26 以前的设备走内存降级，云端恢复仍然可用。
  - 安卓 Chrome 和 WebView 从云盘目录、下载目录选包，按范围读是否可用、速度是否正常。
  - 带上万张图片的整合备份的恢复耗时，和改造前对比。
  - WebDAV 上传后的大小核对，在坚果云、AList、Nextcloud、群晖上各试一次，确认不会误判。
  - 两个标签页：一个在下载或恢复时，另一个启动不会清掉它的临时文件；崩溃后重启会清掉残留。
  - 长时间恢复期间锁屏或切后台，页面会不会被挂起。
- **留给后面的**：原生壳上小于 8MB 的 WebDAV 备份、以及分段失败后的整包下载，仍然整包进内存（第五期）。
