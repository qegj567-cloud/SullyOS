# 主动消息 2.0 · 数据救援（救援模式）

目标与红线见 [主动消息 2.0 总纲](./amsg2-overview.md)。

本地数据被清空、又没有备份时，主动消息 2.0 的 Worker 里可能还留着一部分云端数据。救援模式让账号主人凭一枚临时口令，把这台 Worker 里的全部云端数据解密导出成 JSON。

实现：[`worker/amsg/src/rescue.ts`](../worker/amsg/src/rescue.ts)（导出与留痕）、[`utils/amsgRescueState.ts`](../utils/amsgRescueState.ts)（两端共用的留痕形状）、[`utils/amsgRescueAlert.ts`](../utils/amsgRescueAlert.ts)（前端警告）、[`utils/amsgRescueImport.ts`](../utils/amsgRescueImport.ts)（导回 SullyOS）。回归测试：[`worker/amsg/src/rescue.test.ts`](../worker/amsg/src/rescue.test.ts)、[`utils/amsgRescueImport.test.ts`](../utils/amsgRescueImport.test.ts)。

## 能救回什么

只有开过主动消息 2.0、用自己部署的 Worker 的人才有云端数据。

| 能救回 | 救不回 |
|---|---|
| 角色名、日记、角色发过的消息（最多 28 天） | 完整聊天记录 |
| 开着定时主动消息或挂着排程的角色：最后一次同步时的提示词快照（角色卡、世界书、月度总结、最近一段对话混在一起） | 本地上传的头像、壁纸等图片 |
| 还没结束的那一轮即时对话：结构化的对话消息（这一轮结束后立刻删除；删除失败或这一轮一直没结束时，最多留 7 天） | 记忆宫殿、其他 App 的数据、设置与美化 |
| 排程任务、还没收取的消息 | |
| 云端保存的 API Key、工具凭据、推送订阅 | |

没开定时主动消息、也没有排程的角色，云端的快照只是一句占位符：即时对话每轮把完整内容临时传上去，这一轮结束后立刻删除。这类角色能救回的只有名字、日记、API 配置和角色发过的消息。

角色快照不设过期时间，不会自己消失，不必抢时间。

## 用户怎么操作

1. 打开 Cloudflare 面板 → 主动消息的 Worker → Settings → Variables and secrets → Add，类型选 **Secret**，名字填 `AMSG_RESCUE_TOKEN`，值填一串至少 16 个字符的随机口令（只有自己知道）。
2. 浏览器打开 `https://你的Worker地址/rescue`，输入这串口令，点「开始导出」。页面会下载一份 JSON，并按角色列出可以直接复制的提示词快照、最近对话和日记。
3. 导出完立刻回 Cloudflare 删掉 `AMSG_RESCUE_TOKEN`。
4. 想导回 SullyOS：设置 → 备份与恢复 →「从其他网址 / App 迁入独立用户」，选这份 JSON。点上面那个普通的「导入备份」也一样，都会新建一个用户。

注意事项：

- 救援要在**原来那台 Worker** 上做。云端数据用 `AMSG_MASTER_KEY` 加密，而它只存在这台 Worker 的 Secret 里，Cloudflare 不让读回来。
- 救完之前**不要**点一键部署里的「清空旧数据再装」，那会真的删掉云端数据。也不要先恢复旧备份再重新连上 2.0：旧备份带着旧的连接配置，同步时可能用旧快照盖掉云端较新的那份。
- 救援模式开着时，定时消息暂停投递、过期清理也暂停，导出的就是开启那一刻的样子。删掉变量后下一分钟自动恢复。
- 当初找别人代部署、自己登不进那个 Cloudflare 账号的，需要请当初部署的人操作。
- 打不开 `workers.dev` 地址的网络环境，需要自行解决访问问题（官方中转只服务 App 本身，不转发救援页）。

## 安全设计

### 谁能用

证明「是账号主人」靠的是 Cloudflare 账号权限：只有能给这台 Worker 设 Secret 的人才能开启救援模式。口令是第二道锁：

- 少于 16 个字符视为没开启，救援页拒绝工作，防止弱口令被猜中。
- 口令只从请求头读，不进网址，免得留在日志或浏览器历史里；比对用常数时间。
- 15 分钟内错 10 次就锁 15 分钟。
- 救援接口只读，不改、不删任何业务数据；不带跨域头，别的网站拿不到响应。
- 救援页不含数据，不加载任何外部资源，CSP 只放行本页脚本和同源请求。

### 留痕与警告

每次开启都会留下记录，前端据此强制警告：

- Worker 首次发现 `AMSG_RESCUE_TOKEN` 时开一段新记录，**立刻推送**给云端登记的所有设备。推送跑完才放行导出，所以第一次导出一定排在推送之后。
- 之后每次拉取导出清单、每次读数据、每次口令错误都记账；删掉变量后，每分钟的定时任务会记下结束时刻，再开就是新的一段。
- 记录写不进数据库时拒绝导出：宁可救不了，也不能出现「导出了却没有记录」。
- `GET /config-check` 报出开关状态和这段记录（只有时刻和次数）。这个端点不校验共享密钥，因为共享密钥丢了的时候也必须能看到警告。
- 前端只要发现救援模式开着、或最近一次动静在 7 天内，就强制弹窗：用户必须看满 10 秒才能点确认。新开一段、或同一段里又有导出，确认就作废、重新弹。主动消息设置页在 7 天内常驻一块红色提示。
- 前端把看到的记录存在本地，之后即使 Worker 那边的记录被删掉，本地副本在 7 天内仍会继续警告。

### 这层留痕防得住谁

留痕和警告防的是**会登录 Cloudflare 面板、但不会写代码**的人，比如当初帮忙代部署的朋友、共用账号的人。救援模式把「读出全部数据」的门槛从「会写 Worker」降到了「会加一个 Secret」，留痕就是为这个落差兜底。

它防不住拿到 Worker 脚本编辑权限的人：对方可以直接部署自己的代码，从环境变量里读 Master Key、解密全部数据，全程不经过救援模式，自然也不会留下这里的记录。在这种攻击者面前，Worker 和 D1 里写的任何东西都能被改掉或删掉，包括这里的记录和 Worker 的版本历史。

真正改不掉的只有 Cloudflare 账号之外的东西：

| 记录 | 能否被拿着脚本编辑与 D1 编辑权限的人抹掉 |
|---|---|
| D1 里的救援记录 | 能 |
| Worker 的版本、部署历史 | 能 |
| Cloudflare 账号的审计日志（Audit Logs） | 不能（按官方说法保留 18 个月，且没有删除接口） |
| 已经推送到设备上的通知 | 不能 |
| 浏览器本地保存的警告记录 | 不能 |

所以警告文案让用户去 Cloudflare 审计日志里核实：那是唯一可信的记录。

## 导回 SullyOS

救援文件导回应用时，`utils/amsgRescueImport.ts` 先把它转成一份 v1 纯 JSON 备份，再交给「迁入为独立用户」那条现成的路。不管用户点的是哪个导入按钮，救援文件都**一律迁入为新用户**：救回来的东西比本机少得多，覆盖恢复会把用户清空后新攒的数据整表盖掉。迁入为新用户本来就会给角色换新 id、关掉主动消息任务，导进来不会跟云端打架。

云端没有结构化的角色卡，转换器按 `ContextBuilder.buildCoreContext` 和 `buildFirePack` 写死的小标题把提示词拆回字段：

| 救援文件里 | 导回成 | 说明 |
|---|---|---|
| `tool_pack.charName`、namespace 里的 charId | 角色名、id | |
| 「核心性格/指令」到下一个已知小标题之间 | `systemPrompt` | 只在已知小标题处截断，角色设定里自带的 markdown 小标题不受影响 |
| 「用户备注/爱称」「世界观与设定」 | `description`、`worldview` | |
| 各个「世界书 ·」「扩展设定集」小节 | 一条常驻世界书，挂到角色身上 | 只有当时被激活的条目，关键词和条目划分没了 |
| 「长期核心记忆」逐行 `- [YYYY-MM]: …` | `refinedMemories` | |
| `tool_pack.memories` | `memories`（日记） | 原 id 已丢，换新 id |
| 【最近对话上下文】或即时对话那一轮的 `chat.messages` | 聊天记录 | 取较新的一份；时间前缀按角色时区解读，没时间的按顺序补；图片只剩 `[图片]` |
| `message_outbox` 里快照之后的推送 | 追加到聊天记录 | 只有角色那一方 |
| `llm_credentials` 的 `chat` / `emotion` | 角色对话 API、情绪 API | 地址去掉 `/chat/completions` 还原成 baseUrl |
| 任务或推送里的 http 头像 | 头像 | 本地上传的头像从没上过云，生成默认字母头像 |
| 「互动对象」里的名字和人设 | 新用户的资料 | |

工具凭据（Notion、飞书、MCP 等）不导：迁入为新用户不写全局设置，用户从 JSON 里手动复制。

改拼提示词的小标题（`utils/context.ts` 的 `buildCoreContext`、`utils/activeMsgClient.ts` 的 `buildFirePack`）时，`utils/amsgRescueImport.test.ts` 用真实拼出来的提示词做样本，拆不回来就会挂。

## 改动时的注意点

- D1 大值分块的格式（`\u001famsg-chunks\u001f` 命名空间、根行标记）照抄自上游 amsg-server，上游没有导出。升级上游时 `rescue.test.ts` 里「分块存的大值要拼回完整原文」那一条会先挂。
- 导出的表名只来自 `EXPORT_TABLES` 白名单。新增的上游表要导出时加进白名单，并写明哪几列是加密的。
- 救援路由排在 Worker 入口的最前面，不吃共享密钥那道门：来救数据的人手里正是什么都没有了。
- 即时对话那一轮的快照（`amsg:instant-input` 的值、自排任务的 `taskInput`）里，fire_pack 又单独压了一层 `packedFirePack`，导出时要一并解开，否则文件里最完整的那份设定和对话是乱码。
- 推送 payload 走 `messageKind: 'result'`，`resultKind` 为 `amsg-rescue-alert`；前端在结果分发处认领它，收到后立刻探测并弹窗。
