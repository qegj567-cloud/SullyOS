# 记忆系统概览

## 长篇见面原文与外部清洗

私聊/见面/剧情陪伴的共用提取入口保留每条消息的完整可读内容，不再裁成前 600 字。按实际文本长度约 24000 字符分批（单条完整消息不裁切），兼容长场景与彼方记录混合的手动选区和自动归档。格式错误、截断或请求失败不能当作“没有值得记忆的内容”；自动归档要求全部提取批次成功后才允许存储和推进水位，防止成功批次把失败批次的原文一起隐藏。已生成的旧记忆不会自动改写，可从原文手动重新总结遗漏范围。

外部记忆清洗每批由约 10000 字符缩到 3000，请求超时由 180 秒改为 600 秒。允许完整 JSON 数组外的 Markdown 代码围栏，仍拒绝截断、缺字段和明显缩水的内容；收到完整响应后的格式错误最多重试一次，网络失败/超时不自动重复付费请求。整次搬家仍由调用方在全部批次成功后落库。

本项目包含两套并行运行的记忆系统：传统日度/月度总结（Legacy）和向量化记忆宫殿（主系统）。

## 角色页与像素家园入口

角色宫殿概览现在有「记忆房间 / 像素家园」两页，第二页沿用原像素家园的地图、装修、潜行、人物及导入导出。退出返回同一角色的概览。未启用记忆宫殿的角色也可进入像素家园，不因打开家园而开启记忆提取。原像素存档仍保存在 pixel_home_layouts / pixel_home_assets 和原有角色键中；只移动入口，不重建布局或迁移数据。RoomApp 原位置改为「拜访（测试版）3D」，使用独立的 CharacterProfile.home3D。

聊天加号面板的「记忆归档」按当前角色的 `memoryPalaceEnabled` 判断：启用时先提示该入口属于旧版记忆系统，「确定」返回，「我有必须使用的原因」才进入原归档设置；未启用时直接进入。提示不改变任何记忆配置或数据，不拦截其他归档内部流程。

聊天进入时的 v1「请自查」提示：当前角色开启宫殿且 `activeMemoryMonths` 非空才展示，列出具体年月。按角色在 localStorage `memory-context-self-check:v1:<id>` 记录已答复；「否」和关闭不改记忆，「我看不懂」只显示 DC 反馈指引。「是」通过函数式角色更新移除当前展示的月份，保留并发新增的其他月份，不删记忆或月度精炼。确认后不重复打扰；存储不可用时至少在当前组件会话内不重复。说明明确提醒启用前的历史不保证已进入宫殿，月度精炼不受小眼睛控制。

### APK 中导出记忆宫殿

安卓「导出为 JSON」与设置的全部备份共用 `shareOrDownloadBlob`，直接打开系统分享面板，由用户选择保存或发送的应用；大型文件分片写入分享缓存，不额外写入公共文档目录。取消分享不记作成功，不将应用缓存误称为已保存的备份。网页仍走浏览器分享/下载。实现见 `utils/memoryPalace/saveExport.ts`。

### 可选的相对时间补注

全局配置 `relativeTimeAnnotations` 严格默认关闭；缺失、false、非法配置均不启用。不启用时，提取请求不增加来源编号或提示词、不生成 `relativeTimeAnchor`，正文和召回保持原样。

开启后，私聊手动/自动共用提取入口只为具有有效 `relativeTimeSource` 消息编号、且相对措辞匹配原消息的节点保存来源日期（设备本地日期 key，独立于 createdAt 事件日）。跨消息不同参照日要求模型拆分；无可靠来源时不猜。来源识别仍依赖提取模型。编辑页只读展示参照日与补注，用户只能修改原文措辞或直接写明具体日期，不提供日期编辑控件；旧记忆无来源日期时不补注。

`relativeTime.ts` 根据原文动态生成补注片段，宫殿列表/详情/编辑预览与召回共用规则。原始 content 不混入系统文字，开关不写节点、不调用 API、不重新向量化。紫色日期只读；修改相对措辞后自动计算，直接改写为具体日期则不再补注，无剩余相对措辞时编辑保存清除关联。用户原有日期括号保留。昨天/前天/阿拉伯及中文数字天数按日历日计算，上周按七天前左右，上个月/数字个月前只标年月，去年只标年份。参照日期固定，不随当前日期或用户时区变化重建。

只补活节点（含盒内活节点及便利贴），不补 isBoxSummary 或 archived 节点；封盒二次总结仍读取原文，不把补注烘焙进摘要。开启后的宫殿 JSON 导出 content 包含补注，同时通过 relativeTimeExport.originalContent 保存原文（向量仍对应原文）；导入验证补注与原文相符后恢复原文，保持开关可逆。外部修改过导出正文则尊重修改，不恢复旧原文，也不复用旧向量。关闭时导出格式及正文保持原状。神经链接的关联记忆文本导出也带补注，日常编辑仍读取原文；不关联的传统记忆不变。整机备份继续保存原始节点及来源字段，不改备份恢复逻辑。

### 神经链接：新自动归档关联宫殿，旧档案保持原样

神经链接继续使用同一个 MemoryArchivist，原有日度/月度组织、导入清洗和文本导出保持不变。不迁移旧数据，不另设宫殿列表或旧档案界面。

从本次更新起，常规 processNewMessages 成功存储的节点生成带 palaceMemoryId 的 MemoryFragment，每个节点一条，summary 保留当时正文作为传统模式/源节点缺失的兜底。新链接按源 ID 去重，不合并到同日旧快照；旧导入、历史缺口修复仍生成原来的无链接记录，不追溯绑定。

向量化保存安全：vectorizeAndStore 在写入前验证返回向量完整性，去重后由 MemoryNodeDB.saveVectorizedMany 将整批正文和向量放入同一事务；失败整批回滚，成功后才通知界面并上传远程向量。自动归档在推进水位前读取实际落库节点，因此去重跳过的候选不会形成悬空关联。

宫殿开启时，神经链接通过显式 ID 读取最新正文；编辑共用 updateStoredMemoryNode，正文变更更新向量。导出前重新解析这些链接，输出仍是原来的文本格式；导入仍写普通档案，不自动向量化。删除神经链接条目只移除档案引用，不删除宫殿源节点，确认窗会说明。

宫殿关闭时使用保存的档案文本，原有总结流程继续可用。此时编辑关联记录会将其转为独立传统记录，重新开启宫殿也不会覆盖该修改。宫殿源节点缺失时保留档案文本兜底，不删除档案。节点变更事件只刷新明确关联的新记录，不改动旧档案。

宫殿手动删除单条记忆（含批量删除中的各条）时，若日度档案存在显式关联，询问是否同步删除：选择「是」删除关联档案；选择「否」只移除 palaceMemoryId，完整保留档案原有 summary，成为独立传统记忆；取消弹窗则不删除本条。源节点与档案处理在同一 IndexedDB 事务提交，随后发出增量事件更新 OSContext。无关联的旧档案不做内容匹配或推测。整库清空仍走原有独立流程。

## 系统一：传统日度/月度总结

### 数据结构

- `memories: MemoryFragment[]` — 每日记录（date + mood + summary）
- `refinedMemories: Record<string, string>` — LLM 生成的月度精炼总结
- `activeMemoryMonths: string[]` — 哪些月份的详细日志要注入上下文

### 输入

- **日度记录**：`MemoryFragment`，含 `date`、`mood`、`summary`
- **月度总结**：用户在 `MemoryArchivist` 组件手动点"生成"→ `handleRefineMonth()` 将该月所有日度记录送给 LLM 做精炼（temp=0.3）

### 调用/输出（context.ts → ContextBuilder）

- `buildRoleSettingsContext(char)`（用于情绪评估）：注入全部月度总结 + 当月日度记录
- `buildCoreContext(char, user, true)`（用于聊天）：
  - 月度总结 → "长期核心记忆"
  - `activeMemoryMonths` 对应的详细日志 → "激活的详细回忆"
- `buildCoreContext(..., false)` 仅省略神经链接激活月份的详细日志，月度总结保持原行为。向量召回独立：上游已提供的结果不受 true/false 限制，核心块或实时状态块统一注入；组装器不会因此新增召回调用。记忆宫殿关闭时仍不注入旧缓存。
- AI 可以用 `[[RECALL: YYYY-MM]]` 语法主动拉取某个月的详细日志
- 神经链接 → 角色 → 记忆页的默认折叠「记忆设置」中提供「隐藏 RECALL 指令提示」，按角色保存，默认开启（旧角色未设置字段也按开启处理）。开启仅省略 ChatApp 行为规范中的「调取记忆」一行；关闭恢复该行。本地和云端即时聊天共用此设置，后台主动消息模板保持原行为。指令解析、月份小眼睛、旧版记忆数据与记忆宫殿均不受影响；日记等功能自身的提示也保持原样。此本地偏好随完整备份保存，不随分享角色卡导入/导出。

### 管理

- 用户可切换哪些月份"激活"（控制 token 用量）
- 可编辑/重新精炼月度总结

## 系统二：向量化记忆宫殿（主系统，仿大脑结构）

检索评分对旧档或远程候选中的缺失／非法 `room` 使用客厅评分参数兜底，与提取入口一致；衰减和房间权重共用 `resolveMemoryScoringRoom`。仅在评分时兜底，不改写记忆正文、向量或原房间，不因一条异常记录中断整轮召回。合法七房间的评分保持原样。回归测试见 `utils/memoryPalace/roomScoring.test.ts`。

### AI 原文范围（各入口共用）

`utils/chatContextRange.ts` 是角色原文可见范围的唯一入口：

- **自适应**：读取记忆水位线之后的原文，忽略残留的手动 `contextLimit`；200 / 100 等档位决定整理节奏，不是发送条数的硬上限。
- **手动**：从完整私聊库取最近 `contextLimit` 条，包括已归档原文；不再先用宫殿水位线截断。
- 用户设置的额外起点只能收窄有效范围，过期起点自动失效。
- ChatApp 的 `loadCharacterContextRange` / `computeContextRangeSnapshot` 保持原设计；其他入口直接复用。统一载荷层还会把 UI 提供的 `recentMsgsHint` 与实际可见消息取交集，防止召回、世界书扫描或识图旁路读到范围外原文。`utils/contextEntryParity.test.ts` 对照 ChatApp 与见面发送、重写和感知的最终原文列表验证一致性。
- 需要读取角色近期原文的 AI 功能调用 `loadCharacterContextMessages`；已有完整候选快照时调用 `selectCharacterContextMessages`。聊天、见面（含感知/重写）、通话、剧情角色记忆输入、查手机、日程、彼方、小屋、桌面互动、活动和主动消息等采用同一边界。
- 某个功能明确只需近期片段或设有独立取样条数时，在上述范围**以内**取样，不能借此读取被用户隐藏的原文。剧情本身的独立历史和群聊公共历史仍有各自的范围规则。
- 浏览历史、导出、去重检查、手动总结等操作访问原始记录，不受 AI 可见范围限制。
- ChatApp 主回复在加载范围后及最终请求组装后检查是否仍有有效 user/assistant 消息。自适应范围为空可以是一键归档后的正常状态，不据此读取已归档原文，也不把通话/见面前的旧输入当作待回复消息。确无输入时只提示再发一条消息，不要求用户维护上下文设置，不改水位或记忆。本地聊天和即时对话上云共用此保护，避免 system-only 请求触发上游 `contents is not specified`。实现见 `utils/chatRequestGuard.ts`。
- 一次请求从原文加载到异步 prompt 构建共用同一份水位快照；构建中发生归档只影响下一次请求，不能让已经加载的本轮消息被第二次过滤清空。新消息 ID 证明水位失效时，消息和 IndexedDB 水位镜像在同一事务内提交/清理，再清 localStorage；后台镜像校准也使用单个 assets 事务，避免旧值在清理后被写回。正常水位与重复推送的已有消息不受影响。

手动区间总结面板按 IndexedDB 游标读取一页短预览，全文/日期搜索按需扫描，可取消；不在打开面板时把全角色历史和全文搜索副本装进 React 状态。确认起终点后，只读取选区内的完整消息进行总结，水位线不变。

聊天设置和记忆宫殿的角色设置提供「清理指定范围 / 保留最近 N 条」，独立于总结和副 API：

- 范围选择使用同一分页预览（清理时也包含空消息），按起止消息 ID 选中该角色的全部私有记录，包含两个端点；搜索仅用于定位，不把删除范围缩成搜索结果。也可保留最近 N 条，N 至少为 1。
- 永久删除必须经过两个独立弹窗。第一次核对角色、起止位置、实际条数和水位线之后的记录数；第二次必须完整输入「我确定永久删除我选中的内容」，完全匹配才开放删除。取消或重选会清空两次确认状态。
- 预览只保留待删 ID 和记录指纹；读取和校验以 64 条为一批。确认期间新产生的消息保留；选中的正文或附属内容已变化、消息已被删除时，整笔操作回滚并要求重新预览确认。
- 聊天原文、对应语音缓存及剧情副本引用在一个 IndexedDB 事务中处理。只对完全连续的已选 ID 合并删除，避免跨过其他角色或群聊。已有记忆、收藏、中央剧情正文及其他角色副本保留，水位线和 AI 可见范围设置不变。完成后刷新聊天窗口并标记主动消息云端快照待同步。

关键实现：`components/chat/ChatHistoryCleanupModal.tsx`、`utils/chatHistoryCleanup.ts`；确认校验、并发修改、跨角色隔离和十万条清理测试在 `utils/chatHistoryCleanup.test.ts`。

### 大量归档后的聊天气泡刷新

每条回复气泡落库后，后处理调用 `DB.getRecentMessagesByCharId(charId, 200)` 刷新近期消息。该读取沿 `charId` 索引按消息主键倒序进行，默认排除宫殿水位线之前的原文；这个 DB 参数不直接读取角色的宫殿开关。

近期未归档消息不足 200 条时，游标到达水位线必须立即停止，不能为了凑满窗口继续遍历几万条已归档记录。此前会逐气泡重复扫描旧记录，能造成 API 实际用量已经显示但气泡迟迟出现、相邻气泡间隔过长；同一角色的记录和水位恢复到新站点后仍可能触发。固定拟人打字等待的文字气泡上限为 2 秒，不能用它解释十几秒的重复间隔。

修复仅收窄无效扫描，不修改记忆、原文、水位线或角色开关。显式传入 `includeProcessed=true` 的历史读取仍可读取已归档原文，群聊记录仍不混入私聊窗口。`utils/recentMessages.test.ts` 覆盖一万条已归档记录上的连续刷新、全归档空窗口和显式完整读取。

### 一、仿大脑结构——七个房间

| 房间 | 模拟脑区 | 职责 | 容量 | 衰减 |
|------|---------|------|------|------|
| **客厅** living_room | 海马体 | 日常闲聊、近期互动 | 200 | 快衰减（0.9972/h，1天剩6.5%） |
| **卧室** bedroom | 新皮质 | 亲密情感、深层羁绊 | 无限 | 慢衰减（0.9995/h） |
| **书房** study | 前额叶皮质 | 工作、学习、技能 | 无限 | 慢衰减 |
| **用户房** user_room | 颞顶联合区 | 用户个人信息、习惯 | 无限 | 慢衰减 |
| **自我房** self_room | 默认模式网络 | 角色自我认同演化 | 无限 | **永不衰减** |
| **阁楼** attic | 杏仁核-海马 | 未消化的困惑/创伤 | 无限 | **永不衰减**（潜伏） |
| **窗台** windowsill | 多巴胺奖赏系统 | 期盼、目标、愿望 | 无限 | **永不衰减** |

### 二、存入逻辑（Input Pipeline）

```
角色统一消息时间线（私聊 / 见面 / 通话 / 剧情陪伴等来源共用）
    ↓
[最近N条] ← 热区，直接在上下文中，不处理
[缓冲M条] ← 达到角色档位阈值时触发处理
[已处理]  ← 高水位标记之前的
```

#### Step 1 — 缓冲触发

- 水位节奏按角色独立保存于 `CharacterProfile.memoryPalaceWaterline`，随 IndexedDB
  与完整备份持久化；旧角色缺少该字段时保持默认 `200 / 100`
- 三档预设：线上为主 `200 / 100`、综合 `100 / 50`、见面/剧情为主 `50 / 20`
  （前者为保留原文数，后者为触发缓冲数），另支持小范围自定义
- 管线只看同一 `charId` 下按 ID 排序的语义消息，不按来源建立多套水位线
- 触发检查不只在 ChatApp：私聊回复、见面回复、写入角色时间线的剧情回合、
  通话开场/每轮回复/挂断记录落库后都会在当前入口调用同一管线；主动消息、小屋、
  彼方写入角色时间线后也会触发。检查本身不调用 LLM，只有缓冲达到当前角色阈值才整理
- `PROCESS_RATIO = 0.85`，处理85%，留15%尾部保持上下文连续
- 高水位标记（localStorage）记录每角色处理进度，防重复
- 调快档位后，已有缓冲会在下一次达到新阈值时处理，处理成功前不会先隐藏原文；
  调慢档位不会让高水位倒退或重复提取，原文窗口会随新对话逐渐增长到新档位

#### Step 2 — LLM 提取记忆（extraction.ts）

- 以角色第一人称视角叙事，用户称"TA"
- LLM 输出 JSON 数组，每条含：
  - `content`：第三人称叙事
  - `room`：分配到哪个房间
  - `importance`：1-10（越高叙事越完整，含因→事→反应）
  - `mood`：happy/sad/angry/anxious/tender 等12种
  - `tags`：2-5个关键词

#### Step 3 — 向量化（vectorStore.ts）

- 批量调用 Embedding API（batch=20），模型如 `text-embedding-3-small`，1024维
- **去重**：余弦相似度 > 0.9 视为重复，跳过
- 写入 IndexedDB：`MemoryNode`（embedded=true）+ `MemoryVector`（float[]）

#### Step 4 — 链接构建（links.ts）

- 自动规则（无需LLM）：
  - **时间链**：24h内创建 → strength 0.3-0.5
  - **情绪链**：相同mood → strength 0.4
- LLM 分类（轻量模型，temp=0.2）：
  - 类型：`causal` / `person` / `metaphor`
  - 强度 0.3-0.8

#### Step 5 — 巩固：短期→长期（consolidation.ts）

- 客厅→卧室晋升条件：
  - importance ≥ 8 → 立即晋升
  - importance ≥ 6 且 age > 24h → 时间成熟晋升
  - accessCount ≥ 3 → 频繁回忆晋升
- 客厅超200条 → 按有效重要性（importance × 衰减^小时）淘汰最低者到**阁楼**

#### EventBox 重新整合

- 摘要的 400–700 字是精简目标；超过 900 字只尝试一次二次精简，不再机械截尾并追加省略号。二次精简仍长则采用更短的完整版本，失败、输出截断或混入推理时保留首次完整正文；首次输出本身未完成仍拒绝保存。长摘要照常存储和全文召回，代价是更多上下文 token。此前已截断的摘要不会自动恢复，可用「重新整合」从盒内原始节点重做。
- 超过 3000 字符的盒摘要按不超过 3000 字符分段向量化，各段归一化后按长度加权合并、再归一化，沿用每节点一个向量的存储与远端契约。所有段落参与索引，避免传输层只取前 4000 字；这仍是整盒的语义表示，不保证每个细节都能单独命中。创建、编辑和重建向量共用此路径；任何分段失败都不写入新摘要。普通节点与查询的原有限制不变。
- 自动压缩仍是增量语义：同一未封盒事件的活节点达到 4 条时，用“旧整合回忆 + 新活节点”覆盖 summary；累计事件达到 12 条后封盒。
- 事件盒展开页提供手动“重新整合”：无论是否封盒，都重新读取盒内全部 archived + live 原始节点，**不使用旧 summary**，用于修复总结遗漏或模型推理文本污染。
- 手动重新整合成功后，本次参与总结的原始节点全部归档，保留原文；总结正文、Embedding、节点 archived 标记及盒内 live/archived 列表在同一事务提交。新增归档时 compressionCount 加一，累计归档达到 12 条封盒；只有归档节点的重做不重复增加压缩次数，也不解除已有封盒。整合期间新加入的节点仍保持活跃；原始节点被编辑、删除、移出或盒子被另一轮整合更新时拒绝旧结果，保留原内容并提示重试。
- 新 summary 必须先成功生成向量才会覆盖旧正文；输出若含典型字数计算/推理过程会被拒绝并自动重试一次，两次失败则保留旧 summary。

#### 外部记忆搬家（最多 5 万字）

给从其它应用、设备或记忆系统迁入的用户提供两条入口，共用
`externalMemory.ts` 的保真清洗规则：

- **神经链接 → 角色记忆 → 导入/清洗**：写入传统 `MemoryFragment`；
- **记忆宫殿 → 设置 → 从其它地方搬入原始记忆**：清洗后直接分房间，
  调用 Embedding API 写入向量节点，并建立时间/情绪/人物/因果/隐喻关联；
  同时复用全自动总结水位线的 `buildAutoArchiveFragments` +
  `mergePalaceFragmentsIntoMemories` 桥接逻辑，把同一批内容按日期写入当前
  角色的神经链接传统记忆档案。

外部文本没有聊天 `Message ID`，因此双写记忆但不推进
`mp_lastMsgId_*` / `hideBeforeMessageId`，也不会隐藏任何聊天记录。

单次输入上限 50,000 字，字数由前端按 Unicode 字符在本地统计。上限内按约
10,000 字的自然段边界自动分批调用副 API；超过上限时不发起任何 API 请求，
而是按总字数建议需要拆成几批，并提示优先在日期或完整事件段落之间切开。
提示词的首要约束是“只整理时间和结构，不压缩内容”：不得摘要、合并、
去重或省略人物、地点、数字、对话、动作、因果、顺序与情绪细节；长事件
宁可连续拆成多条，也不能用一句结论替代原文。格式与保真是并列硬目标：
搬家路径只接受完整 JSON 数组与完整字段契约，不使用通用解析器的截断对象
抢救；输出正文相对原批次明显缩水时也会拒绝。格式/完整性失败会自动重试
一次，仍失败则整次不入库并保留输入，避免出现“前几批成功、后几批丢失”
的半份搬家。

### 剧情事件盒手动转为角色记忆

事件盒列表中，每个盒子的「重新总结」使用主 API 重新读取该盒起止消息 ID 范围内的完整原文，不使用旧摘要。自动归档与手动重做共用正文检查：不回退读取 reasoning_content，剥除显式思考标签，拒绝空正文、输出截断、上游过滤及典型字数推理泄漏。总结请求为思考模型预留最多 4096 输出 token，摘要提示仍限制在 800 字内；每次点击只发起一次请求，失败后可手动重试。

重做成功后只原位替换该盒摘要，保留盒 ID、创建时间、原文归档标记、转化回执和其他盒子。提交时重新校验摘要来源与原文；原文缺失、被修改或剧情被删除时拒绝保存，保留现有数据。已转为角色记忆的内容不会被重做同步覆盖，需在神经链接／记忆宫殿单独修改；空摘要盒也能进入列表重做。回归见 `storyTheaterArchive.test.ts` 和 `storyTheaterArchivePanel.test.ts`。

剧情会话右上角「查看事件盒与转化记忆」及剧情列表的事件盒按钮进入独立页面。只展示 summary 策略产生的事件盒，支持展开摘要、勾选导出 TXT、选择参与角色，并为每个选中的盒子填写记忆日期。没有事件盒时说明生成条件，向量策略仍走原独立向量入口。故事无需结束，也不切换真实/虚构模式。

`storyTheaterMemoryConversion.ts` 复用正常水位线的 `extractMemoriesFromBuffer`、`vectorizeAndStore`、`buildAutoArchiveFragments` 和神经链接合并规则。完整事件盒摘要拆成小段再提取，避免抽取器单条 600 字截断。LLM 按目标角色视角二次整理，明确区分用户、扮演身份与其他人物；正文保留剧情来源，日期由用户指定，不把剧情时间写回聊天时间。

开启宫殿时写入带向量的节点，并以 `palaceMemoryId` 关联神经链接；关闭宫殿时只写 `mood='story'` 的传统记忆，不调用 Embedding。手动操作不要求自动归档开关打开。不会推进 `mp_lastMsgId_*` 或 `hideBeforeMessageId`，也不隐藏、删除原文。

以「剧情 ID + 事件盒 ID + 接收角色 ID」防重：同页执行锁 + 事务内回执检查。宫殿正文、向量、神经链接及 `archives[].memoryConversions` 回执同事务保存，只有成功后才更新界面与发布远端向量；空提取、向量失败、源摘要变更或角色配置变更均不留下半份记录。同一次多盒转化逐盒提交，失败时保留已完成盒，重试只处理未完成项。语义去重跳过的节点不生成悬空神经链接关联，回执展示跳过数量。

回执随完整剧情备份保留；删除剧情不反向删除手动转入角色的记忆，删除页会提示。回归：`storyTheaterMemoryConversion.test.ts`、`storyTheaterArchivePanel.test.ts`、`db.storyTheater.test.ts`；实际界面 + IndexedDB、模拟 API 验收页 `test/fixtures/story-archive.html`（独立端口 5191）。

### 三、检索逻辑（Retrieval Pipeline）

**查询源清洗（querySanitizer.ts）**：query 构建前先过 `sanitizeQuerySourceMessages`——图片/表情包/语音消息整条剔除（图片 content 是几万字符的 base64 data URI，进 embedding 批量请求会把 token 总量顶爆，硅基流动直接 400 code 20015），卡片类消息经 `normalizeMessageContent` 翻成可读文本，文本里的 data URI 也一律剥离。入库管线的 `isMessageSemanticallyRelevant` 是同一口径。

**Embedding 请求防线（embedding.ts）**：单条截断 4000 字符（防单条超 8192 token）；按批内字符预算（6000）+ 条数上限（10）切批（防「每条合法、合批总量超限」类 400）；批量仍被 400 拒时自动降级为逐条向量化并把完整错误响应写进 console.error 日志，逐条后仍失败会在报错里指明第几条、多长、内容开头。**保险丝触发必有用户可见提示**：截断、降级成功（"已恢复、结果完整"）都走 console.error 进设置里的日志面板（面板只捕获 error 通道），有测试钉死不许静默。

```
最近3条消息(≤500字) → 查询构建
        ↓
   ┌────┴────┐
向量搜索(85%)  BM25关键词(15%)    ← 混合检索
   └────┬────┘
        ↓ 融合分数
   房间权重加权打分               ← 每个房间不同权重侧重
        ↓
   扩散激活(Spreading Activation) ← 沿链接找关联记忆，最多+5条
        ↓
   情绪启动(Mood Priming)        ← 匹配当前mood的记忆×1.3
        ↓
   反刍检查(Rumination)          ← 概率性从阁楼冒出1条创伤记忆
        ↓
   格式化输出 → 注入System Prompt
```

### 四、认知消化过程（高级仿脑机制）

#### 认知消化（digestion.ts）

每 50 轮聊天自动触发 + 随时可手动触发（无冷却限制）。触发后在聊天界面弹窗反馈消化结果。消化是**纯状态机**——只改变现有记忆的状态，不再向宫殿写入概括：

- 阁楼创伤 → 解决（移入卧室）/ 加深 / 淡化
- 窗台期盼 → 达成（移入卧室）/ 失望（移入阁楼）
- 自我反刍 → 新困惑（新建阁楼节点，进入状态机循环）

**回看窗口（消化的主输入面）**：上次消化以来（`mp_lastDigest_` 时间戳）新增的客厅+卧室情景记忆（≤30 条，时间正序）作为 `[E*]` 材料——"聊天总结成一条条记忆，消化 = 回头看这些记忆、二次悟出什么"。产出走已有出路，带硬上限（宁紧勿松，防阁楼通胀成焦虑症）：

- `worry`（≤2）→ 担忧上阁楼，进状态机循环
- `aspire`（≤1）→ 新期盼上窗台，进期盼生命周期
- `distill`（≤2）→ 跨时间稳定的二次领悟，带 `plate_room` 提交对应门牌
- `keep` → 绝大多数经历就只是经历

概括类产出**改道门牌**（不再新建 MemoryNode——语义写回情景库会变成"泛情感高 imp 记忆"污染召回，这是历史上近似重复词条的根源）：

- 书房知识内化 → 提交「我是谁」门牌
- 用户信息整合（synthesize_user）→ 提交「TA的事」门牌
- 自我领悟（self_insight）→ 弹窗昭告保留 + 提交「我是谁」门牌。**不再追加 `char.selfInsights`**（该字段已冻结为只读遗留，存量照常注入）

被消费的源节点打 `digestedAt` 标记退出候选池（旧数据靠衍生节点 sourceId 反查兜底）。

**消化日志（DigestReport）**：每次消化落一条报告——审视了哪些材料、状态机改了什么、往门牌提交了什么、门牌实际更新了哪几块。存 `digest_reports` 表（每角色留最近 30 条），记忆宫殿 App「认知消化」卡片里可回看。

#### 期盼生命周期（anticipation.ts）

```
active(新建) → anchor(7天+，心理锚点) → fulfilled / disappointed
```

#### 共激活学习

多条记忆被同时检索时，它们之间的链接强度 +0.05（最大1.0），模拟记忆网络强化。

#### 连接精度与备份内存（2026-10-15）

`memory_links.strength` 写入时保留五位小数；建链规则、连接数量、ID、两端和类型不变，
不截断候选、不删弱连接。单次舍入误差最多 0.000005，反复共激活的 +0.05 仍按原规则累加。
导入旧备份、导出副本共用 `compactMemoryLink`；「优化资源存储」可按每批 500 条整理存量连接，
同事务读游标当前值再更新，失败可重试。备份本身不修改原库，也不要求先点优化。

精度选择脚本：`node scripts/audit-memory-link-precision.mjs`。固定随机种子，10,000 组查询、
每组 200 个候选/3 个种子，比较原始与 3～6 位权重的联想 top3。
五位在该合成样本中 top3 入选集合完全一致；50,000 条样本边的 JSON 减少约 7.21%，
gzip 减少约 35.25%。这些是连接样本的体积，不是整份备份、IndexedDB 磁盘或浏览器内存的节省比例；
极接近的分数仍可能换序，模拟不等于真实对话质量评估。

全备份/纯文字/媒体备份的数组表共用单事务游标逐条处理，按 500 条或 4M 字符分片，
不再先把所有表放入 `backupData`。向量在全备份也使用两遍游标生成原有 Float32 二进制，
不改变向量精度；单例表、设置和协同会话元数据保留既有组装逻辑。
`backupArchive.ts` 把分片及媒体暂存为 Blob，依次读入压缩；输出以最多 1 MiB 的 JS 缓冲
组成 Blob 分块，不拼一整根 ZIP Uint8Array。图片/语音保持原字节，v3 manifest 与旧导入器兼容，
纯媒体仍是补丁语义。压缩器与 WASM 回退随应用打包，不依赖 CDN。

这限制的是临时 JS 对象/字节缓冲，不保证浏览器总内存恒定：最终 Blob、旧 Base64 去重键、
向量合并后的紧凑 bin、单条超大记录仍有成本，旧图去重键在压缩前释放。导入仍组装完整数据后恢复，
本轮不把导入端宣称为流式，也不以桌面通过替代 iOS Safari 真机验证。

### 五、房间门牌（Room Plates — 情景→语义固化层）

**解决的问题**：房间里存的全是情景记忆（带时间戳的事件），走相似度召回是"抽卡"——对用户的了解永远碎片化，取决于本轮抽到什么。人脑不是这样：朋友不会去回忆"哪次谈话你说过家里的事"，他就是*知道*。缺的是情景记忆固化成语义知识的那一步。

**方案**：四个房间头上各有一块"门牌"（`room_plates` 表，`roomPlates.ts`）——房间装原始经历（召回细节），门牌写沉淀出的常驻认知（每轮直接注入 System Prompt，不走召回、不衰减）：

| 门牌 | 房间 | 内容 | 上限 |
|------|------|------|------|
| 「TA的事」 | user_room | **角色卡测试**：把用户当一张空白角色卡，只有必须写在卡上的内容才收——基础信息、家庭结构、重要他人、人格冲击级的重大节点。阶段性状态/情绪分析/性格侧写不收（那是印象档案的领域） | 12条 |
| 「我是谁」 | self_room | 角色对自己的稳定认知 | 10条 |
| 「我们之间」 | bedroom | 关系的**质地**。硬规则：禁止给关系命名（prompt 约束 + 合并层窄正则兜底） | 10条 |
| 「我的领域」 | study | 会什么、在学什么 | 8条 |

客厅天生短暂不配门牌；阁楼/窗台已有生命周期状态机（本质就是它们的门牌）。

**更新时机（两者都有）**：
- **EventBox 压缩/封盒**（eventBoxCompression Step 9）→ 盒子结论增量合并进所属房间的门牌。"进行中的线"活在盒子里，封盒的结论才毕业成语义事实——边界不是分类问题，是生命周期问题
- **认知消化**（digestion 尾声，含无材料早退分支）→ 四块门牌一次 LLM 调用全量整理

**合并语义**（`mergePlateEntries`，纯函数可测）：LLM 每次输出完整新列表，旧条目不被重新输出即淘汰（硬容量上限 = gist 记忆的容量压力，边界判错的条目会被自然挤出）；`basedOn` 引用旧条目则继承 `firstLearnedAt` / `sourceCount+1`（保留"什么时候得知的、被印证几次"）。

**送达保证**：消化提交的候选（源节点已打 `digestedAt`，不会来第二次）在整理 LLM 失败/输出为空/漏掉某房间时**机械兜底并入**（`fallbackMergeSubmissions`：去重+容量+卧室规则照常，不改写），绝不静默蒸发；消化日志里"提交了但门牌没更新"会显示 ⚠️ 状态行。

**长期用户防灌爆**：消化候选池按时近取上限（书房/用户房/自我房各 20 条、阁楼按重要性 12 条）——prompt 不被老积压撑爆。

**老用户历史回填（Bootstrap）**：老积压不白攒，但**只走手动**——记忆宫殿 App「整理历史记忆到门牌」按钮，**每按一次清一小段（5 批）**，进度存 localStorage（`mp_plateBootstrapBatch_`）断点续传，随时可停、下次接着清，全部清完打 `mp_plateBootstrapped_` 完成标记。不做自动触发：上千条记忆的用户不该在毫无预期时看到一长串回填批次。机制：四个门牌房间的历史按**时间正序**分批（12 条/房/批）过整理 LLM——后面的批次带更新的事实，合并语义自然 supersede。每房间历史上限 240 条（超出丢最旧）；合并幂等，重复回填不翻倍；每次 LLM 尝试 120s 硬超时。

**注入**：`injectMemoryPalace` 每轮纯 IDB 读出 → `char.roomPlatesInjection` → `buildCoreContext` 在印象档案之后注入（受 `memoryPalaceEnabled` 把关防残留）。注入框架把门牌定位为 **constraint 而非 topic**："你早已知道的背景，不要主动提起，只在相关时自然影响反应"——对应人脑背景知识"常在但低激活"的状态。

**家园聊天入口**：`homeConversation.ts` 直接调用 ChatApp 的 `buildChatRequestPayload`。`home_3d` 与 `chat_app` 共用交互召回策略、完整可见消息范围及注入位置；每次使用请求内角色副本清空旧召回和门牌。共用 `injectMemoryPalace` 在检查 embedding 配置前读取门牌，因此开启宫殿但未配置向量时，私聊和家园都能读到门牌。家园只替换现场/动作及输出协议提示词。

**审计**：神经链接 app「门牌」标签页（`RoomPlatePanel`）可查看/改写/删除——蒸错的事实一旦常驻会被自信地重复很久，必须有人工纠错口。一键清空（wipe）会连门牌一起清。

**备份**：门牌与消化日志都随「设置-导出」全量备份走（v2 分片，导出装配在 OSContext、还原在 `importFullData`，clear-and-add 语义）；门牌另随记忆宫殿导出/导入迁移（`export.ts`，合并语义：同文本去重、尊重容量上限、条目重生成 ID）。

## 本轮召回修补（记忆链接）

聊天加号面板的「记忆链接」用于修补刚才回复实际使用过的记忆：

- `recallReceipts.ts` 记录每轮真正注入 prompt 的 memoryId；修补入口只读取当前用户消息之后最近的一张回执，没有回执时不会退回上一轮。
- 独立记忆可直接原地修改；命中 EventBox 任一节点时，会展开盒摘要、全部活跃子节点和全部归档子节点，归档状态不影响编辑。
- 修补现场显示独立记忆日期、事件盒日期范围及每个盒内节点日期；盒摘要置顶，其余活跃/归档节点按日期排列，诊断 API 也会收到每个候选节点的日期。当前可靠粒度是“日”，不展示常作为占位值的 12:00，以免伪造精确时分。
- 保存补丁后用当前 Embedding API 为同一 memoryId 重新生成向量，并同步已启用的远程向量库。
- 记忆宫殿详情页与「记忆链接」共用 `updateStoredMemoryNode`：正文没变时只保存 metadata、零 API；正文变化时才发起一次单条 Embedding 请求。Embedding 失败不会先写入新正文，避免文本与向量失配。
- 「？？？」诊断显式使用 `ContextBuilder.buildCoreContext(char, user, false)`；调用前清空旧制记忆、月度总结、向量召回注入、房间门牌与 buff。候选材料只来自本轮回执及其命中事件盒的完整结构，不会再次调用向量召回。
- 「？？？」保持引路者身份，但诊断回复借用当前角色的语言节奏与措辞；面向人时使用“你”或用户名，提及当前角色时使用角色名字，不把双方称作“用户/角色”。归档节点明确标记“已归档，本轮未注入”。
- 引路者形象直接复用角色在小屋里的 `sprites.chibi`；没有配置 Chibi 时才显示光点。形象下只标“？？？”，不把引路者写成角色本人。
- 引路者的进场问候和过场文案按角色 `personalityStyle` 从本地固定文案中稳定选择，不调用 LLM；只有用户主动描述错误并请求排查时才调用主 API。
- 显影动画可在入口右上角设置中永久跳过，偏好保存在 `os_memory_repair_skip_animation`。
- 打开入口时先关闭聊天加号面板；退出整个记忆链接时再次清空面板状态，保证落回聊天正文。线索编辑抽屉的关闭只返回本次修补现场，不会丢失诊断结果。

关键实现：`components/chat/MemoryRepairPortal.tsx`、`utils/memoryPalace/memoryRepair.ts`。

### 3D 家园上下文与后处理（2026-10-04）

- `homeConversation.ts` 与 ChatApp / DateApp 共用 `loadCharacterContextRange` 和历史格式化；自适应遵守水位快照，忽略旧手动条数，用户断点继续收窄。开启宫殿本身不强制覆盖用户的手动模式；模式沿用统一设置。`contextEntryParity.test.ts` 对照三个入口的最终原文及召回材料，覆盖超过 200 条、手动区间、断点和一键入宫。
- 家园用户发言、角色回复与主动开口各自保存为独立的 user / assistant 消息；相邻短动作保留原文、合为一段场景记录，发言、其他 App 私有消息、主动开口触发及归档边界都会切段。动作段不算角色发言，不调用 LLM 压缩。新回复不再追加到旧问题的消息 ID。
- v3 同步保持角色日志与共享消息库同事务提交。旧 v1 / v2 消息保留 ID、归档水位和用户断点，附加原始事件；共享历史格式化先筛选范围，再按事件时间展开旧记录、恢复双方角色，之后插入世界书深度。无法从日志还原的旧消息保留原文，不猜测拆分或删除。
- 家园生成前复用 ChatApp 的本机收件准备；补回/重生成不能用临时新 ID 将范围外的旧记录带回。只有尚未落库的新输入可作本次请求的临时输入。重生成及旧输入补回按目标输入时间截断后续原文。
- 已归档动作段不再追加；一键存入记忆在读取历史快照的同一事务中封住动作段，避免归档进行中追加的内容被旧水位吞掉。后来的动作另起新消息，不改动归档提取算法或档位阈值。
- 3D 家园此前只落库、未挂接整理（旧文中的世界家园 engine 是另一入口）。现在 OSContext 的角色保存成功后调用 `homeMemoryPostHook.ts`：新消息段或新角色回复检查共用整理阈值，读取最新宫殿开关，复用 `processNewMessagesWithAutoArchive`；新回复累计共用认知消化轮次。重存、编辑、动作不重复计对话轮次，连续动作段也不会按每个动作增加消息条数。按角色排队，保存失败不会触发，未到阈值不调用整理 LLM。
- 2026-10-05：3D 家园使用独立 Trace 标识 `home_3d`，与 `chat_app` 共用完整载荷、交互召回增强和实时数据注入。旧 `world_home` 仍指另一套世界家园，不扩大其策略范围；DateApp 也保持原策略。范围先按 ID 水位/断点筛选，之后按 timestamp（同时间以 ID 打破平局）排序；两边的召回、世界书扫描和历史格式化均消费此顺序，不使用 UI 近窗替代。


### 情绪上下文的入口边界

ContextBuilder.buildEmotionContext 统一组装 buffInjection 和共享缓存 innerState。仅 chat/home 入口且角色日程功能、情绪开关开启时注入；未声明入口默认不注入。私聊与家园的实时块复用此函数，不清空其他入口的角色状态。innerState 使用同一情绪评估落库函数写入的角色缓存，下一轮实时读取，不依赖当天日程是否存在。私聊和家园重生成显式省略旧情绪输入，并重新评估。家园评估与主回复并行，评估看到本轮实际发送的 system 和历史。


### 全入口日程上下文

ContextBuilder 的 buildCoreContext、buildVolatileCoreState、buildRoleSettingsContext 为异步入口，调用方必须 await 后再拼接或发送。角色日程功能开启后统一按角色时区从 IndexedDB 读取当前日程，注入全天安排、当前时段和日程旁白；false/skipMemories 不控制日程。没有日程只返回空日程段，不调用 LLM 生成。关闭角色日程总开关才停止读取与注入。

私聊的日程放在 ContextBuilder 实时状态块中，不再在 ChatPrompts 额外拼接；后者在每轮建立一次日程读取 Promise，交给 ContextBuilder 和音乐氛围共用；null 也复用，不跨轮缓存。日程修改指令仅提供给有对应解析器的私聊，其他入口照样得到日程内容。时间感知关闭只隐藏钟点，不隐藏安排。后台 fire-pack 将日程读取延后到 worker 真正执行时，避免把打包时的旧状态冻结在提示词中。

## 低频维护（可选）

记忆宫殿全局配置/角色记忆设置底部折叠项「低频维护」提供默认关闭的全局开关。
开启后暂停常规自动提取与自动认知消化；召回仍读取已有记忆，尚未处理的聊天原文保留。
角色设置中的弹窗按「提取 → 逐盒压缩 → 门牌」逐次点击推进，每步成功后停下等待；
压缩每次只处理一个达到阈值的盒子，不连带整理门牌。步骤按角色保存在本机，关闭后可续上。
认知消化仍可在原入口手动运行。关闭开关后恢复原有自动流程。

本页宫殿副 API 与 Embedding 请求共用最小间隔（默认 60 秒，可调）；这是发起间隔，
不是第三方账户的全局 RPM 保证，不控制其它页面/设备、主聊天或已提交的云端任务。
等待发生在请求超时计时前；手动模式门牌留在本地执行。Embedding 429 不立即重试。
提取失败不推进水位，摘要向量化失败不覆盖旧摘要或归档活节点，失败步骤可稍后重试。
