# 角色自定义时区

角色卡里可以给角色单独设一个时区（角色编辑页 →「角色自定义时区」开关 + 时区下拉）。开启后，注入给这个角色的「当前时间 / 今天几号 / 现在是白天还是深夜」都按 ta 所在地折算，而不是跟着用户手机走。

典型场景是异国恋：用户在中国，角色设定在纽约。用户这边晚上 9 点，角色那边是同一天的早上 9 点，两边看到的钟本就不该一样。

没开这个开关的角色，一切照旧跟随设备时间。

## 时间感知开关与架空剧情

神经链接角色编辑页的「聊天 · 时间感知强化」和「线下时间感知（约会）」分别控制线上聊天和见面请求。两者默认开启，关闭其中一个不会影响另一场景的开关。

- 聊天时间感知关闭时，不再给模型附加当前真实时间、历史消息的现实时间戳或互动间隔提示。
- 线下时间感知关闭时，见面的感知开场、发送与重新生成都不附加历史消息的现实时间戳、今日实时日程、神经链接记忆的年月日标签或记忆宫殿召回中的现实日期与「今天/距今X天」标注。感知开场也不再根据现实互动间隔跳时，或提示「现在是深夜/清晨」「如果刚聊完」，改为沿用最近记录中的剧情时间、地点与事件。
- `ChatPrompts.buildMessageHistory` 默认使用聊天开关；见面通过 `options.timeAwarenessEnabled` 显式传入线下开关，避免线上设置影响线下历史。

这些开关只控制请求中附加的时间信息。数据库时间戳、界面收发时间和备份仍保留；用户原话、旧回复、记忆或卡片正文里已经写下的日期与时间也不会被自动删除。

### 剧情陪伴的收发时间

剧情设置页的「真实时间陪伴」不再提供角色日期选择，也不再为新参与者生成日期锚点。页面明确提示输入与回复按各自实际发送时间记录，正文中的虚构日期不改变聊天记录的时间或顺序；「虚构剧场」默认关闭记忆输入且不自动写入角色正常记忆，用户可以从事件盒显式选择转化。虚构剧场在开启记忆输入或使用独立向量召回时，不会将角色的今日实时日程、携带原文的现实时间戳、其他剧场副本的 `<scene_header>` 或归档节点的现实日期注入提示词；场景条 `<scene_header><time>` 仅承接本剧情前提、常驻事件盒、上一层剧场正文以及用户本轮明确写出的时间推进。旧条目中的 `characterMemoryDates` 保留兼容。

事件盒手动转化的「记忆日期」必须由用户填写，使用 `parseLocalDateKey` 校验，沿宫殿现有日期语义存为该设备本地日中午；这是日级归属，不表示真实收发时刻。跨多日摘要当前统一归入用户填写的那一天，模型输出的日期不能覆盖它。只设置新记忆的 `createdAt`，不改任何原消息时间、角色剧情锚点或聊天水位；记录实际转化时刻使用 `Date.now()`。

`story_theater_memory` 是写入角色共享历史的剧情副本。它的 `Message.timestamp` 必须与中央原件的实际收发时间一致；角色设定的剧情日期单独放在 `metadata.theaterTimelineTimestamp`，不能用于共享历史排序或现实互动间隔。新副本统一通过 `createStoryTheaterMirrorMessage` 创建。

旧版本曾把「角色剧情日期 + 距条目创建的时长」写入副本的 `timestamp`，可能把昨晚的剧情排到今天线上输入之后。启动、读取共享历史及备份导入/导出时，`storyTheaterTimeline.ts` 会在同一事务里按有效的中央原件引用校正副本，并保留正文、ID、原剧情日期和记忆水位线；事务失败全部回滚，下次可重试。

校正的索引读取失败时，先等待事务完整回滚，再以主键游标扫描重试一次，兼容主表仍可读但索引不可用的旧库。不删索引、不升级数据库、不清数据；原件读取或写入失败仍报出原始错误，不冒充修复成功。此回退不能修复浏览器底层存储损坏。

找不到原件或引用不匹配时，不推算真实日期，也不删除记录：请求不为该旧副本附加现实时间戳或用它计算互动间隔。线上请求另按持久化 ID 把错排在待回复输入之后的旧剧情放回原来的轮次，避免模式切换与「继续说」提示被旧剧情带偏。普通迟到回复、家园事件及定时主动消息仍保留原有顺序。已经生成的记忆摘要和正文中的日期不自动改写。

## 两把尺子，别混用

改动任何跟时间有关的代码前，先分清这个时间代表谁：

| 代表谁 | 例子 | 该用什么 |
|--------|------|---------|
| **角色那边几点** | 角色此刻在做什么、ta 的作息、prompt 里的「现在是」、角色写下的时间戳 | 角色时区 |
| **用户自己的时间** | 状态栏时钟、桌面日历、消息气泡上的收发时间、导出文件的时间 | 设备时间 |
| **跟时区无关** | 「距上次聊天多久」这类纯时长差 | 绝对时间戳直接减 |

判断不了的时候问一句：这个数字是给角色看的，还是给用户看的？

## 基础件

都在 `utils/` 下，别自己手搓时差：

| 函数 | 用途 |
|------|------|
| `timezone.ts` → `resolveCharTimeZone(char)` | 取角色生效的时区 id；没开开关返回 `undefined`（= 跟随设备） |
| `timezone.ts` → `nowInTimeZone(tz, base?)` | 返回一个 Date，用**本地** getter（`getHours()` 等）读出来正好是 `tz` 的墙上时间 |
| `timezone.ts` → `wallClockToTimestamp(text, tz)` | 上一条的逆运算：把「角色当地的墙上时间」文本还原成真实时刻 |
| `timezone.ts` → `tzAwarenessNote(tz)` | prompt 里那段时差提示 |
| `scheduleTime.ts` → `getScheduleWallClock(char, base?)` | 角色墙上时间，`nowInTimeZone(resolveCharTimeZone(char))` 的快捷方式 |
| `scheduleTime.ts` → `getScheduleDateKey(char, base?)` | 角色所在地的日历日 `YYYY-MM-DD` |
| `scheduleTime.ts` → `getCurrentScheduleSlotIndex(slots, char, base?)` | 按角色时间找当前时段 |
| `dailySchedule.ts` → `getDailyScheduleForChar(char, at?)` | 按角色的日历日读日程，带旧 key 兼容 |
| `localDate.ts` → `getLocalDateKey(date)` | 日期 key。注意别用 `toISOString().slice(0,10)`，那是 UTC 日 |
| `hooks/useLocalDateKey.ts` → `useLocalDateKey(tz)` | 组件里用的响应式日期 key，跨午夜自动刷新 |

### `nowInTimeZone` 返回值的坑

它返回的 Date，**绝对时间戳是被挪过的**——只有用本地 getter 读字段才有意义。所以不要再把它的 `getTime()` 喂给另一个同样会折算的函数，那样时差会被减两遍。要真实时刻就用 `Date.now()`。

## 日期 key 的写读一致性

日程存 IndexedDB 用的 key 是 `${charId}_${dateKey}`。**写入和读取必须算出同一个字符串**，否则会「写进 A、读 B」，每次打开都判定没日程、反复调 LLM 重新生成——烧 token 而且从界面上看不出来。

写入侧统一走 `getScheduleDateKey(char)`，读取侧统一走 `getDailyScheduleForChar(char)`。

`dailySchedule.ts` 里还有一层旧 key 兼容（更早版本按 UTC 日、接入角色时区前按手机日）。迁移时会校验 `generatedAt` 确实属于角色当地的今天，并且把旧记录**搬走**而不是复制——留副本的话，等角色当地日历翻到那个日期，同一份日程会被当成两天用。

## 已接入的地方

用户所在地节假日感知是例外：其日期按用户设备时区计算，后台由 tool_config 带入用户时区，不能使用角色时区。普通日期不额外注入，见 [节假日感知](user-holidays.md)。

聊天注入、见面（VN 模式 + 感知开场）、打电话、实时信息（时间/天气/节日）、日程全链路（生成、卡片、桌面组件、小小窝、小屋、聊天里的日程注入、音乐氛围）、角色自由活动、定时消息解析。

## 还没接的

下面几处目前仍按设备时间走。不影响日常使用，但角色开了自定义时区时会出现「同一份 prompt 里两个时间打架」。

### 主动消息（改之前先确认 amsg2 分支的状态）

| 位置 | 现状 |
|------|------|
| `context/OSContext.tsx` 主动消息触发段 | 写进隐藏系统提示的「现在是 X」取设备时间，而同一次请求里 `buildSystemPrompt` 注入的是角色时区的时间。这条 hint 会落库，之后几轮上下文里都留着 |

改法：拿 `resolveCharTimeZone(char)` 折算；注意别把用来算时间差的 `now` 一起换掉，那个必须继续用真实时刻。

主动消息 2.0 那条链（`utils/activeMsgClient.ts` 的 `buildFirePack`）已经接好了：模板带一个 `tzId`，worker 到点渲染的每个时间都以它为参照系（`utils/amsgFirePack.ts`）。凡是「打包这一刻」的状态都不烤进模板，改由 `AMSG_SLOT_*` 槽位到点现算 —— 当前时间、日程当前时段、此刻在听的歌、今日节日 / 天气 / 热搜都走这条路，见 `ChatPrompts.PromptBuildOptions` 上那张表。

其中今日节日按角色时区判「今天几号」，并且跟着角色的「时间感知」开关走（关掉的角色到点也不会知道今天是圣诞节）——这个开关随 `tool_pack` 上云，见 `worker/amsg/src/realtimeWorld.ts`。热搜的时段划分则固定按 `Asia/Shanghai`：榜单本身就是国内的作息，worker 跑在 UTC 上，不指定的话「今日上午」会差好几个时段。

### 一组角色共同排日程（feature request）

来自用户反馈：设定成一家人的多个角色，日程是各排各的——同一时刻打开，一个在画画、一个在盘算偷东西、一个在发呆，谁也不知道谁在干嘛。「一家人」只存在于人设文字里，日程上看不出他们有关系。希望能在生成日程时把同组角色一起生成，至少让晚饭这类时刻凑得到一块。

做之前想清楚的地方：全部对齐容易变成几个角色在同一时刻说同一件事的复读，比各活各的更假。比较稳的形态是共享少量锚点（晚饭、集合、出勤），其余时段仍各排各的。

顺带一提，日程卡上「NOW」标的是**当前这个时段从几点开始**，不是当前几点。同一时刻打开三个角色的卡，NOW 会分别停在 10:00 / 11:00 / 11:30，因为各人这段活动的起跑线不同。卡片头部现在直接显示当前时间，就是为了避免把 NOW 那行的数字当成钟来读。

### 界面上的「钟」该跟谁

这几处是产品判断，不是纯 bug——先想清楚这块表是挂在角色屋里还是用户桌上：

- 小小窝直播看板的电子钟、表盘天色（清晨/白天/黄昏/夜晚）
- 「查手机」里角色手机主屏的大时钟和日期
- 见面「感知」页顶部的星期 + 时间
- 梦境「一天最多看 N 个」的配额按哪一天清零

小小窝判断「角色睡没睡」已经改成跟角色时区了。如果看板的钟继续跟设备走，会出现看板写着「营业中 / ON AIR」、表盘却是月亮的观感冲突，两者一起定比较好。

### 测试还没盖到的

- 日程生成的**写入侧**：prompt 里那句「今天是 X (星期 Y)」和落库用的 `date` / `id`
- `nowInTimeZone` 本身没有直接的单测

## 已知限制：设备夏令时空档

`nowInTimeZone` 是先读出目标时区的年月日时分，再用**设备时区**重新构造 Date。如果那个钟点在设备时区当天恰好不存在（夏令时往前跳的那一小时），JS 的 Date 构造器会静默往后推一小时。

触发条件：用户设备在有夏令时的地区，角色所在地此刻的钟点正好落进设备当天被跳过的那一小时。后果是时段判定漂 1 小时，一年一次、持续一小时，且通常在角色那边的凌晨。

根子是「用本地 Date 承载异地墙上时间」这个设计——那个钟点在设备时区没法表示，怎么补偿都只是挑一个近似值。目前按已知行为留着。

秋令时那个重复的小时不受影响，`getHours()` 读出来仍是对的。

### 3D 家园光照

3D 家园自动天色按房主角色时区运行（`Home3DView` → `resolveCharTimeZone` → 编辑器 `roomLighting.js` → `nowInTimeZone`）。无自定义时区时跟随设备；同屋多个居民共用房主时间。光影面板可固定清晨/白天/夕阳/夜晚作为本机预览，恢复「自动」后重新读取当前时刻。自动时段边界和跨时区逻辑由 `room3dTimeLighting.test.ts` 覆盖。
