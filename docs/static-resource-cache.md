# 静态资源缓存与网页更新

## 设计

资源缓存模块装在 `worker/sw-keep-alive.ts` 这个 SW 里，和推送共用同一次注册。它只读写自己名下的 Cache Storage，不碰 IndexedDB、推送订阅和别的应用缓存；网络失败时返回真实的失败，不拿空内容顶替。

- Vite 构建产物放在 `assets/build/`，与 `public/assets/` 分开。只有构建生成、带内容 hash 的目录使用一年 immutable。
- 构建结束后扫描发布目录，生成带 SHA-256 和大小的资源清单，嵌进最终的 SW。入口 HTML、桌面与恢复用设置及其同步依赖预缓存（2026-10-10 构建约 18 个文件、4.5 MiB），模型、WASM、游戏等资源用到时再缓存。构建标识与网页一起注入，每次部署都能触发更新。
- 已安装的页面使用同一发布版本的入口与核心资源，避免入口先升级而 SW 还是旧的。SW 自动检查更新并在后台下载。版本号（`utils/appVersion.ts` 里 `APP_VERSION` 的前半截）变了的更新会弹提示，用户确认后接管并刷新；版本号没变的更新不打扰正在用的人，下次打开或刷新页面时直接就是新版。其他标签页不会被强制刷新。点过「稍后」的提示不会被后台的自动检查重新弹出来。在设置里手动检查更新时，不管版本号变没变都会给出更新入口。从旧的推送专用 SW 升上来时走同一套规则。
- 未变的资源按内容版本跨发布复用。保留当前、最近一个旧快照、上一份完整启动快照以及仍有标签页在用的入口快照；最近一个旧快照未下载完时，也不能挤掉上一份完整快照。遇到不会响应版本询问的老页面，推迟旧快照清理。清理由启动完成的页面发消息触发，不放在 SW 激活的时候做：激活期间页面的请求都得等着，那里只做接管。按需缓存最多 96 MiB / 256 项，单个文件最多 16 MiB，30 天没用过的会过期；超过上限时先淘汰最久没用过的资源。存储失败时照常返回网络响应。
- 只缓存构建清单里的同源 GET 资源和明确列出的公共 CDN 资源。API、带凭据的请求、Range、失败响应、no-store/private、opaque 响应都不写缓存。带查询参数的同源请求不接管，两个例外：图标的 `?v=`，以及入口页面本身（通知点开的 `/?openApp=…` 也从缓存的入口启动）。
- 设置里提供检查更新、缓存用量和清理按需缓存。
- Tailwind 3.4.17 浏览器运行时放在本地，保留现有的动态类名能力。首页的外部字体和数学样式异步生效，不阻挡主模块与首屏；外部字体和素材首次离线没有保证，字体可以回退到系统字体。离线不提供 AI/API 服务，也不保证能打开从没加载过的功能。

### Tailwind 动态样式生成

`public/vendor/tailwind-3.4.17.js` 带一处本地补丁：生成任务串行执行，编译期间的 DOM 变化合并到下一轮，配置和 `text/tailwindcss` 的重建请求也会保留。生成失败后，下次请求会重新扫描全部类名。

原版运行时会并发写同一个虚拟输入 `/template.html`。在 iPhone Safari 上，页面插入元素后，新手引导紧接着添加高亮类，就能让后一轮覆盖前一轮尚未读取的类名；前一轮又已经把这些类名记为处理过，结果 `w-3`、`h-3` 等规则永久漏掉，SVG 会撑到数百像素。这种竞争也可能发生在其他连续 DOM 更新中。

替换或升级这份 vendor 文件时，需要保留串行生成的保证，并运行 `pnpm vitest run scripts/tailwind-runtime.test.ts`。测试使用真实的运行时编译器，控制 MutationObserver 的通知顺序，覆盖高亮、连续更新、配置变化、自定义样式变化和失败恢复。只给某个图标补宽高不能修复其他漏掉的样式。

### 聊天美化的首次渲染

聊天和群聊模块携带预编译的基础 utility 样式（`components/chat/chatRuntime.generated.css`），不用在 DOM 出现后等浏览器 Tailwind 编译才能得到输入栏、滚动区和按钮布局。它内嵌在聊天代码中，首次渲染时插入，不增加独立 CSS 下载请求，也不属于桌面预缓存和首屏静态依赖；不带全局 preflight，仍保留运行时生成其他动态类名。`pnpm build:chat-preview` 同时生成预览和聊天运行样式，发布构建也执行此步骤。

美化中的本地图片最多 4 路读取。`BlobRefStyle` 只通过 CSSOM 替换图片属性中的 blobref URL，保留字体声明、布局规则和 !important；不再因图片读取完成而重写整个 style 文本。隔离 Edge 对照验证：旧实现会将已加载字体对象重建为 unloaded，新实现保持同一个 loaded 对象；该实验两种实现均只发起一次字体请求，不能据此声称每次都会重复下载字体。返回、换 CSS 和延迟读取结束后的 URL 仍按消费方释放，不改保存或导出内容。

这些处理减少已经确认的现场编译等待和字体声明重建，不会等待全部字体或美化资源才进入桌面。作者 CSS 中的外链字体、@import 和图片仍可能受外部网络、响应头或字体大小影响；没有受影响作品和设备的资源记录，尚未定位该用户全部掉字体与卡顿的原因。字体规则被添加或移除会相应改变 CSS-connected FontFace，参见 [CSS Font Loading](https://www.w3.org/TR/css-font-loading/#font-face-css-connection)。

### 下载与校验

启动清单用 4 路并发下载，每个文件 20 秒超时。全部依赖成功后才写入口 HTML，所以缓存里有入口就代表这一版能离线启动。

下载中断或入口校验失败时，保留这一版已经下载并校验通过的文件，仅移除入口 HTML 的完成标记。下次重试或 SW 重启后复用这些文件，只补齐缺失部分；缓存的构建 JS 仍要重新校验，坏副本按文件清理并重取。不保留截断响应里的半个文件，也不把未完成快照显示为离线就绪。多个页面同时请求准备启动缓存时，共用同一次下载，避免重复下载与完成标记竞争。旧快照清理额外保护上一份完整启动快照，并限制未被页面使用的旧残留。

首次安装时 SW 立刻生效，推送和保活不用等下载；页面随后在后台让它把启动资源下好，失败了可以在设置里重试。升级时反过来：新 SW 先下启动资源、下完再等用户确认。下载失败也照常装上，不让存储问题挡住推送逻辑的升级；这一版接管后入口先从网络加载，页面同样会在后台补下启动资源，补好之前不能离线启动。

- 入口页面从站点根路径取，不请求 `/index.html`：有的托管平台会把后者重定向到根路径。
- 除入口页面外，每个文件都要大小和 SHA-256 与清单一致才写缓存。入口页面允许被托管平台改写（比如注入统计脚本），只要它引用的 `assets/build/` 文件全都属于本次构建就接受。
- 带内容 hash 的文件直接复用浏览器的 HTTP 缓存，页面刚下载过的不会再下一遍。固定名称的文件每次向服务器确认是否有变，不会被旧的 HTTP 缓存（包括 `force-cache` 读取）顶替。
- 清单内的构建 JS 在交给页面执行前，也必须校验完整字节数和 SHA-256（包括 Cache Storage 命中）。截断、同长度但内容不同、读取流报错都不能透传成可执行响应。异常副本只按该资源 key 从本模块的缓存移除，再用 `cache: reload` 绕过 HTTP 缓存重取一次；仍不完整则返回网络错误，并让下次入口加载检查新版，不无限重试。安装更新复用旧 JS 时同样校验，坏的 HTTP 缓存不能一直阻止更新。
- 公共 CDN 资源只保存能读到内容的成功响应，一天内直接复用，之后先给缓存、后台再更新。只有以 CORS 方式发出的请求（`fetch`、带 `crossorigin` 的标签）会被缓存；普通跨域 `<img>` 拿到的是 opaque 响应，不缓存。音视频的 Range 请求直接走网络。

### 站点发了新版之后

旧页面仍会引用发布时的 hash 文件。只上传新构建会让未曾缓存的懒加载功能立即失去旧文件；自动刷新只能在用户已经被打断后补救。

GitHub Pages 和 Cloudflare Actions 发布在 `pnpm run build` 完成后，运行 `scripts/prepare-retained-build-assets.mjs`，把近期完整构建的 `assets/build/` hash 文件按原路径一同发布。默认窗口为 7 天，另设最多 32 个构建、5,000 个不同文件和 256 MiB 的上限；触及上限时按整个旧构建淘汰，不拆散 JS/CSS/资源依赖。入口 HTML、SW 和 public 固定名称文件仍用本次产物，历史文件不加入新 SW 的清单。历史内容按 SHA-256 校验并去重，同路径不同内容会阻止发布。

历史目录通过 GitHub Actions cache 在成功部署后保存；Pages 与 Cloudflare 使用独立 key，避免混合相对路径和根路径构建。Pages 只允许仓库默认分支发布，Cloudflare 只允许 master；同一站点不交替发布不同分支的孤立历史。工作流不会因下一次 push 中断正在部署并保存历史的任务。第一次发布或 cache 被回收时只能保存当前构建；日志会显示实际保留量。这是有限的兼容窗口，不保证全部用户能连续使用旧页面 7 天，也不能恢复此前已删除的资源。Vercel、手动上传等其他发布方式需要自行在构建后、上传前运行同一个脚本，并持久保存 history 目录。

超过保留窗口或没有历史文件时，旧页面仍可能遇到 404。SW 看到这种响应就记下「这一版已经被替换」，之后入口页面和不带 hash 的固定名称文件（主题、图标等）都改成先走网络、断网时才用旧版的缓存，让新页面拿到跟它配套的文件。这样 `utils/chunkLoadRecovery.ts` 的自动刷新能直接拿到新页面，不会卡在旧入口上。这个标记存在该版本自己的入口快照里，SW 重启后还在，随该版本一起清理。浏览器明确离线时不发起自动整页刷新，也不消耗刷新冷却额度；错误页提示联网后手动重试，联网事件本身不会触发刷新。

### 什么时候提示更新

要同时满足两条才弹提示。第一条是确实有东西可换：有一个下载好、正在等待接管的新 SW，或者控制页面的 SW 比页面新（别的标签页已经换过，刷新就能跟上）。页面比 SW 新的时候不算，这时刷新什么也改变不了，要等新 SW 下载完。版本新旧靠构建标识开头的构建时间比较，见 `vite.config.ts` 里的 `appBuildId`。第二条是新版的版本号和页面的不一样；新 SW 自己带着版本号，页面问它就知道。

版本号没变时不需要用户确认，流程是这样的：新 SW 下载完会告诉当前的 SW「新版好了」，当前的 SW 看版本号相同，就把自己标成「已被替换」，之后入口页面改走网络。于是用户下一次刷新或打开，一次加载拿到的就是新页面，不会中途重载。新页面发现等待中的 SW 和自己是同一个构建，就让它接管，这一步在后台完成、不刷新页面；接管要等旧 SW 空闲下来，一般在页面启动后几十秒内。断网时刷新仍然是旧版从缓存启动，等联网后的下一次加载再换。所有页面都关掉再打开的话，新 SW 直接接管，入口从它自己的缓存启动。

有一种情况下版本号变了也不弹：旧版已经被判定为「被替换」之后用户自己刷新。这时页面是从网络拿的新版，它和等待中的新 SW 是同一个构建，所以按上一条在后台接管。此时旧版的功能已经打不开了，没有理由再留在旧 SW 上。

### 首屏依赖与部署兜底

2026-10-10 资源审查发现，3D 更新新增的 `three-mesh-bvh` 被放进通用 vendor，经静态依赖把 Three 引擎带回桌面首屏；PDF/PSD 解析器与小岛 UI 也混入通用 vendor。它们现在分别随对应功能按需加载。多入口构建中的独立 `chibi-wardrobe.html` 不属于 OS 启动清单；发型编辑器、捏人数据和 3D 引擎仍在资源清单中，用到后缓存。设置继续预缓存，保留离线恢复入口。

本地正式构建首屏静态 JS 约从 5.55 MB 降至 3.78 MB（未压缩代码），启动清单从 35 项 / 12.8 MiB 降至 18 项 / 4.5 MiB。这是构建产物比较，不是 iOS 真机耗时比较，也不代表已经定位所有组件加载故障。数据库和 SW 仍并行启动，桌面不等待离线资源准备。

Cloudflare 部署使用 assets-first，正常文件直接由静态资源服务返回，只有缺失路径进入 `worker/static-site-not-found.ts`，返回 `404 + Cache-Control: no-store`。不能开启全局 SPA HTML 回退：曾实测缺失 JS 返回首页 HTML、200 和一年 immutable；仅关闭回退仍会被目录规则加上一年缓存，所以缺失文件需要独立兜底。OS 导航保留同一页面地址，通知使用首页查询参数；首页、恢复页和独立衣橱均是实际存在的文件。CI 限制不能添加 `run_worker_first` 或静态资源 binding，避免正常启动请求绕到脚本。新配置上线后仍需实测生产响应；它不会主动移除用户 HTTP 缓存中已有的错误响应。本地 Wrangler 实测正常入口及脚本返回 200，缺失脚本返回 404 / no-store；隔离 Edge 在屏蔽外部 CDN 时可启动，缓存准备后可断网重开。85 项相关测试通过，拆分后的 3D、PDF、PSD、UI、聊天和设置模块均可执行。这些验证不覆盖真实 iOS WebKit 故障。

### 构建

`vite build` 自己会生成带清单的最终 SW，不依赖部署平台先执行 `build:workers`。两处打包 SW 用的是同一份 esbuild 配置（`scripts/worker-bundle-options.mjs`）。开发服务器不启用资源缓存，用 `pnpm build` 后 `pnpm preview` 检查。原生 App（`vite build --mode capacitor`）的文件本来就在安装包里，也不启用：它用的是 `public/` 里那份只管推送的 SW，设置里不显示缓存面板。

入口：**设置 → 备份与恢复 → 网页更新与资源缓存**。缓存下来的离线资源可能被浏览器回收，不能代替数据备份。缓存里记的时间是绝对时间戳，表示最后一次使用（一天内的重复使用不重复记），与角色时区无关。

## 验证范围

### 数据库打不开但界面像被清空

`Index with the same ID already exists` 是 WebKit 读取 IndexedDB 内部索引元数据时的错误，不是应用层同名索引的 `ConstraintError`，也不能据此认定 3D 资源触发配额驱逐或记录已被删除。网页拿不到数据库连接时，不能通过 bump schema、删索引或删库重建来承诺恢复。先保留原设备、浏览器、原网址和备份，采集系统版本、浏览器与错误信息。不要让用户清网站数据、卸载浏览器或覆盖旧备份。

2026-10-08 排查：3D 发布 `1706962e` 相对发布前 master `0e8d3534` 将主库 v72 升至 v74，新增 `messages.charId_source` 与 `messages.charId_homeTurn` 两个非唯一复合索引。新建索引需要处理既有消息；尚未在受影响 iOS PWA 上复现内部 ID 冲突，不能据此认定迁移已损坏数据。静态缓存自身不打开主库。PR #733 曾改为先检查主库、再注册 SW；没有证据证明缓存并行造成重复索引 ID，且串行化会推迟 SW 和后台就绪。2026-10-09 缩小调整范围：入口并行准备主库与 SW，后台写入仍等两者就绪；DatabaseGuard 共用入口的只读检查，桌面只等数据库，不等 SW 或离线下载。浏览器自行触发的 SW 更新不受入口顺序完全控制。上述调整不构成受损库恢复或根因修复。

`utils/databaseOpenDiagnostics.ts` 先在内存记录阶段，主库检查结束后择空闲时批量保存；不在 open/upgrade 回调里读写 localStorage，也不等待诊断落盘。支持 idle callback 时最长等 2 秒，否则延后 1 秒；页面隐藏或 pagehide 时尽力保存。每页使用独立 localStorage key，通常保留最近 8 次页面会话、每次 16 条，另存最近打开成功、只读检查成功、升级提交三个检查点，并兼容读取旧 v1 记录。字段仅含页面/请求编号、完整构建 ID、设备绝对时间戳及相对耗时、阶段、版本、固定错误类别、standalone/browser 和页面前后台/bfcache 状态；不含记录内容、异常全文或密钥，不上传。localStorage 拒绝访问时保留本页内存记录；系统强杀而未触发保存时可能缺记录，不能把缺记录当作未发生。

失败页和「设置 → 底部版本信息 → 本地数据库诊断」都可手动复制，恢复后也能提供成功阶段；正常启动不读取历史诊断。相同完整构建的错误→成功用于识别同构建重开恢复；构建变化只说明加载新代码后恢复，不能证明补丁生效。upgrade-started 里的目标版本不等于已提交；应查看同页面/请求的 committed/aborted 和后续 open/read-ready。旧构建没有记录，不能补推过去的故障。同网址与同显示模式也不能单独证明浏览器和 PWA 使用同一份存档。

`DatabaseGuard` 在主界面及其 Provider 挂载前，打开现有数据库并以 readonly 事务检查核心表可读性；失败展示独立诊断，不继续加载空桌面。`openDB` 后续失败也会通知保护界面，即使业务调用方吞掉了异常。入口后台任务同样等待读取检查，角色读取失败后停止默认角色、后续迁移与启动补传。保护页不读取聊天内容、不清存储、不上传诊断；手动复制只含构建、网址路径、浏览器与错误信息。这是失败保护，不是浏览器内部数据库修复，不承诺已损坏存档可恢复。

参考：[WebKit SQLiteIDBBackingStore.cpp](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/Modules/indexeddb/server/SQLiteIDBBackingStore.cpp)。测试：`utils/databaseHealth.test.ts`、`utils/databaseGuard.test.ts`；独立失败 fixture：`test/fixtures/database-guard.html`（模拟 open 错误，不连接用户数据库）。

### 主程序加载前的纯黑屏

`scripts/startup-recovery-plugin.ts` 把无依赖的 `public/startup-recovery.js` 内联在入口头部，早于主模块和 Tailwind。入口模块解析/初始化失败时，React 内的报错面板本身也无法启动；此时显示独立的启动诊断和手动更新按钮。12 秒后根节点仍空也显示等待/恢复入口；主程序随后成功挂载时立即收起，不覆盖正常聊天，也不自动循环刷新。

已经困在旧入口的用户可以打开**同一个站点路径下的 `recover.html`**（根目录站点为 `/recover.html`，GitHub Pages 为 `/SullyOS/recover.html`）。不要让用户换域名来修复，存档按原域名保存。此页不依赖主模块；检查更新复用原 SW 注册，只调用 update 与已有的 `SULLY_ACTIVATE_UPDATE` 协议，接管后返回原站首页。不注销 SW、不删除缓存或数据库、不修改推送订阅。网络失败/安装超时保留重试按钮。

App 内的「资源加载失败」页也提供「检查更新并修复」入口，普通刷新仍失败时可直接进入同站恢复页；路径随部署 base 生成，兼容根目录与 GitHub Pages 子目录，原生 App 不显示此入口。`Unable to preload CSS for …` 只说明该样式依赖未加载成功，不能凭这一行区分旧 hash 文件缺失、网络中断或响应类型错误，更不代表聊天记录损坏。历史文件保留和 SW 缺失资源恢复已覆盖 CSS；需结合失败网址、构建信息和实际响应继续定位。

诊断仅本页显示，在用户点击时复制，不上报；包含构建标识、浏览器、无查询参数的页面路径和启动错误。它提供排查入口，不能仅凭纯黑屏认定某个用户一定是缓存问题。
