# 使用统计

SullyOS 官方部署（`qegj567-cloud.github.io` 和 `sully-os-nu.vercel.app`）接了一套自托管
[umami](https://umami.is/)，用来数「哪个页面被打开了、哪个功能被用了一次」。

这份文档说清楚三件事：**收什么、怎么关、怎么自己核实**。改任何统计相关的代码前先读完。

## 一句话版本

不用 cookie、不存 IP，永远不碰你和角色的任何对话、记忆、设定。
只数计数，外加一组浏览器自己测出来的「页面加载有多快」。

不叫它「匿名统计」，是因为严格说这不算匿名——[往下看](#这是假名不是匿名)。

## 为什么要收这些

SullyOS 的功能已经多到一个人扫不完了，而我们对「哪些功能真的有人用」几乎没有概念——
社区里说话的永远是那一小撮，剩下的人用得怎么样、卡在哪，全靠猜。这套统计就是拿来补这一块的。

具体想回答的问题，跟收的字段一一对应：

| 想知道什么 | 靠哪部分数据 | 会导致什么决定 |
|---|---|---|
| 哪些功能压根没人用 | 「打开某功能」的分布、各选项的当前使用者数 | 砍掉没人用的，把维护精力挪到有人用的地方 |
| 需要配置的功能有多少人真配成了 | 各功能的「开 / 配了没开 / 没配」分布 | 「配了却关着」多说明引导在某一步劝退了人，该修；「压根没配」多说明这功能没人要，可以砍 |
| 大家配置的时候卡在哪一步 | 测试连接 / 重置 / 重试的成败链路 | 哪一步劝退最多就重做哪一步的引导 |
| 性能优化值不值得做 | 记忆条数、单角色聊天条数、本地存储占用的区间 | 比如有多大比例的会话扛着 500+ 条记忆，决定要不要做虚拟滚动 |
| 本地数据会不会被系统清掉 | 存储水位和持久化许可的组合 | 「快满了又没拿到许可」的人多，就该在界面上更主动地催备份 |
| 首屏在真实设备上有多慢 | 页面加载 / 交互响应的耗时（浏览器自测） | 开发机上永远是快的，只有真实用户的数字能说明该不该继续拆包、砍启动时的活 |
| 兼容性投入投在哪 | 装成 PWA 全屏运行的比例、系统 / 设备分布 | iOS 全屏那堆安全区和键盘坑还值不值得继续填 |
| 哪些预设是白做的 | 气泡样式、聊天壳、顶栏样式等的当前使用者数 | 下次做新预设之前，先知道上一批有没有人用 |

**不会拿来做的**：用户画像、个性化推送、广告、给第三方。我们也可能会定期把部分统计图在社区里公开。

如果你不介意，**把设置里那个开关留着开**对我们帮助很大——上面这些判断全靠它。
不想参与就关掉，功能一点不受影响，我们也不会再问第二次。

## 代码在哪

| 东西 | 位置 |
|---|---|
| 唯一的上报出口、开关、档位换算 | [`utils/analytics.ts`](../utils/analytics.ts) |
| 会话级快照（外观 / 角色设置 / 功能启用 / 数据规模）取什么、怎么收敛成枚举 | [`utils/analyticsSnapshot.ts`](../utils/analyticsSnapshot.ts) |
| 启动时决定要不要挂统计脚本 | [`index.tsx`](../index.tsx) |
| 「打开了哪个 App」+ 五条会话级快照的触发时机 | [`context/OSContext.tsx`](../context/OSContext.tsx) |
| 设置页的开关 | [`apps/Settings.tsx`](../apps/Settings.tsx) |
| 回归测试 | [`utils/analytics.test.ts`](../utils/analytics.test.ts)、[`utils/analyticsSnapshot.test.ts`](../utils/analyticsSnapshot.test.ts) |

**全仓库只有一个埋点出口**：`utils/analytics.ts` 里的 `trackEvent()`，它内部是
`window.umami?.track(...)`。所有埋点都调 `trackEvent`，没有第二条路。想知道到底会发出什么，
读这一个文件加上全仓库对 `trackEvent` 的调用就够了。

出站请求里唯一不走这条路的是[页面性能](#页面性能)——那条由 tracker 自己测、自己发。
它同样受设置里的开关管，靠的是 `data-before-send` 那道闸门（见
[什么情况下一个请求都不发](#什么情况下一个请求都不发)）。

这么设计不只是为了好读——调用点没法绕过开关判定，关掉之后不可能有漏网的。

## 数据发到哪

自托管的 umami 实例：`https://stats.friedsully.com`（站点 id `3f775277-882d-4453-be2c-3226eddab438`）。
后台只有维护者能进，不接任何外部服务。

这两个值**不写在源码里**，由构建环境注入：

| 部署 | 怎么配 |
|---|---|
| GitHub Pages | 仓库 Variables 里的 `UMAMI_SCRIPT_URL` / `UMAMI_WEBSITE_ID`，由 `.github/workflows/deploy-pages.yml` 传给构建 |
| Vercel | 项目环境变量 `VITE_UMAMI_SCRIPT_URL` / `VITE_UMAMI_WEBSITE_ID` |

之所以不硬编码：写死在源码或工作流里的话，任何人 fork 过去一构建，他的用户就会朝这个地址发请求。
放进 Variables 之后 fork 拿不到值，构建出来天然是零统计的版本——**「二改的实例不统计」靠的就是这一层**。

## 数据存多久

原始记录保留 12 个月，到期自动清理；长期只保留不含任何明细的月度汇总数字，用于跨年对比。
这是服务器侧的配置，仓库代码里看不到，和「IP 不落库」一样属于靠承诺和可审计性保证的部分
（见[这是假名，不是匿名](#这是假名不是匿名)一节）。

## 什么情况下一个请求都不发

`initAnalytics()` 里五道早退，任意一条中了就直接返回，**连 script 标签都不创建**：

1. **构建时没配环境变量（二改）**。`VITE_UMAMI_SCRIPT_URL` 和 `VITE_UMAMI_WEBSITE_ID` 两个都配齐才会加载。
   官方部署在构建环境里配，自部署默认没有——所以你自己部署的实例是零统计的，不用做任何事。
2. **用户在设置里关掉了**。
3. **浏览器开了 Do Not Track**。不用动开关，自动跳过。
4. **维护者自己的开发机**。hostname 是 `localhost`、`127.x`、`192.168.x` 这类局域网地址时不统计，
   自己跑 build + preview 或者真机联调点出来的数据不进正式库。
5. 已经挂过一次了（防重复）。

tracker 标签上还挂了 `data-do-not-track="true"`，作为第二道保险——
万一以后加载路径改了，这层不会跟着一起失效。

脚本已经加载之后还有一道闸门：`data-before-send` 指向的那个函数，tracker 每发一条都要先过它，
开关关着就返回空、当场不发。它拦的是**性能指标**——那条是 tracker 自己在页面隐藏时发的，
不经过 `trackEvent`，所以「会话中途关掉开关」这个场景只有这道闸门拦得住，不然得等到下次启动才干净。
（这条有测试钉着，见 `analytics.test.ts` 里「会话中途关掉，tracker 自己发的性能指标也当场停」那条。）

## 不按域名做白名单

umami 的 tracker 支持一份主机名白名单（`data-domains`）：hostname 不在名单里，脚本在浏览器里
就直接不发，一条数据都不会有。这里**没有**挂它。

原因是有人会因为网络原因挂自己的域名反代官方站，那也是真实用户，按域名卡等于把这批人整个丢掉。
而「二改的实例不统计」由构建时环境变量那层保证（见[数据发到哪](#数据发到哪)），
不需要域名再挡一次；开发机由上面第 4 条单独挡。

代价是：**你从哪个域名打开的，会跟着记一笔。** umami 每条记录都带 hostname，这一项关不掉。
官方那两个域名无所谓，但如果你用的是自己的域名，那串字符就进了统计库——它不含你的身份，
可一个自定义域名往往只对应一个人，属于[假名](#这是假名不是匿名)那一档。
介意的话在设置里关掉统计，或者开浏览器的 Do Not Track。

页面访问只记路径：tracker 挂了 `data-exclude-search` / `data-exclude-hash`，URL 的查询串和
`#` 后内容一概不采集。推送通知的深链会把 `activeMsgCharId=<角色id>` 挂在参数上，
角色 id 是稳定标识，必须从源头挡住，而不是赌「清参数的代码赶在上报之前跑完」的时序。
（这条有测试钉着，见 `analytics.test.ts` 里「不采集 URL 查询串和 hash」那条。）

另外刻意关掉了 umami 自动发的页面访问（`data-auto-pageview="false"`），改由我们自己显式发一次。
tracker 自己会往外发的就只剩性能指标那一条（见[页面性能](#页面性能)），其余全部经过
`trackEvent`，审计时不必去推断 tracker 会不会背着我们多发。

这里用的是 `data-auto-pageview` 而不是 `data-auto-track`：后者会把 tracker 的整个初始化一起跳过，
性能指标的观测器就挂不上了。代价是 tracker 会带上它自带的点击上报——那套只认元素上的
`data-umami-event-*` 属性，仓库里一个都没有，所以它一条也发不出来。**想让某个按钮自己上报请照旧调
`trackEvent`**，别去挂那个属性，不然就绕过了「所有上报都在一个文件里」这层收敛。
（这两条都有测试钉着，见 `analytics.test.ts` 里「不挂 data-auto-track」那条。）

## 每条记录都带产品版本号

tracker 挂了 `data-tag`，值是 `utils/buildInfo.ts` 里 `APP_VERSION` 的版本号那半截（`v3.0`，
代号只在设置页展示，不进标签）。面板里能按它把数据切开看。

主要是给[页面性能](#页面性能)用的：两个版本的数字混在一起，「这次优化到底有没有让首屏变快」
就问不出来。顺带也能看新版发出去之后铺开得多快。

它是写死在代码里的一个字符串，同一版的所有人完全一样，不带任何个人特征——
所以它**不算**[假名](#这是假名不是匿名)那节里说的「维度」，不会把关联窗口撑大。

> 发版前记得改 `APP_VERSION`。不改的话新旧版本的数据会堆在同一个标签下，
> 上面那两个问题就都答不了了。构建 hash（`BUILD_LABEL`）是自动的，不用管，
> 也别拿它当标签——每次提交一个新值，面板会被撑爆，而且那个粒度细到能区分人。

## 本地存了什么

只有 `localStorage` 里一个 `os_analytics` 键，内容是 `{"enabled": true/false}`——
**开关本身的状态**，跟其他设置（`os_theme`、`os_api_config`）一样是你自己的偏好。

统计**不给自己记账**：「数据规模每会话最多报一次」的节流标记只是个内存变量，
标签页一关就没了，不落 localStorage、不落 IndexedDB、不落 cookie。
（这条有测试钉着，见 `analytics.test.ts` 里「统计不给自己记账」那条。）

## 收集频率 vs 统计周期

客户端只管**每次会话丢一票**，不含任何周期假设。想看月度分布就在 dashboard 里把日期范围框成
一个月，想看周报就框一周——周期住在查询侧，客户端一行代码都不用动。

正因为不含周期假设，它才兼容一切周期。反过来把「每月一次」做进客户端，就得在浏览器里
记「上个月报过了」，那才是真往用户设备上写追踪状态。

### 五条快照轮流出场

数据规模 / 当前外观 / 当前角色设置 / 当前功能启用 / 当前SAR与聊天输入这五条，**一次冷启动只报其中一条**，
随机挑，另外四条这次不报。

五组分别最多带 8、38、38、34、10 个属性，统计库按「事件 × 属性」逐行保存。一次只报一组，
平均约 25 行。SAR 的十个状态单独参与轮转，不加宽原有功能事件，也不额外增加一次启动的
事件数；各组样本仍可用于判断「多少人开了 X」。

挑哪条用的是随机数，不是「记住上次报的是哪条」——后者要跨页面加载保留状态，就得往用户设备
上写东西，跟上面那条自我约束冲突。样本量一大，五条的分布自然就均了。

代价在跨事件关联：如果多条在同一次冷启动里发出，可以直接对着看；现在一次只有一条，
「开了 MCP 的人数据规模多大」这类交叉问题得靠同一个 session 里的多次冷启动凑齐，
覆盖率不如从前。真要做这类分析单独想办法，别把五条合成一条——合了只是事件数从五条变一条，
属性还是那一百多个，库里一行都不会少。

顺带说一下口径：每会话采 = **会话加权**，重度用户票多。这对多数决策反而是对的权重
（「有多大比例的会话扛着 500+ 条记忆」问的就是压力，不是人头占比）。

要按设备去重也行，查询时 `COUNT(DISTINCT session_id)` 就够——umami 的访客哈希在一个自然月内
是稳定的。**但别把范围框成跨月**：盐在月初轮换，同一台设备跨过月初会变成新 id，
框「过去 60 天」会把一个人算成两个。跨月对比请按月分开统计再比。

## 永远不会收集

- 你和角色的任何对话内容、记忆、角色设定、你的设定
- 你在任何地方输入的文字、表单内容
- **任何配置的内容**：API 地址、密钥、token、账号名、cookie、你给服务器起的名字、
  城市名、数据库 ID。这些一个字都不出去。
  会数的只有「这个功能开没开、配了几个、用的哪家（写死在代码里的枚举）」
  —— 见下面的[当前功能启用](#当前功能启用)
- **报错原文与堆栈**。崩溃兜底、加载卡死这类情况只记「在哪出的」和「哪一类错」两个
  写死的代号，报错文本留在 console 和你自己的剪贴板里，不进上报
- cookie；IP 不落库（反代的 access log 也关掉了 IP）
- 跨站追踪、录屏、热力图（umami 自带这几样，我们不开）

## 这是假名，不是匿名

这两个词在数据保护里有确定的分工，差别不是修辞：

| | 意思 | 后果 |
|---|---|---|
| **匿名**（anonymous） | 处理后**再也**关联不到任何个人，不可逆 | 已经不算个人数据，GDPR 这类法规不再适用 |
| **假名**（pseudonymous） | 单看数据认不出是谁，但配合其他信息仍能关联到同一个人 | **仍然算个人数据** |

**这套统计属于后者。**

先说 umami 本身：它不写 cookie，访客身份是服务端算的一个哈希
（网站 id + 主机名 + User-Agent 等 + 一个**每月初轮换**的盐）。所以**同一台设备在一个自然月内
本来就是同一个 id**——这是 umami 统计访客数和回访率的基础，不是我们额外加的。

在这之上，`当前外观`、`当前角色设置`、`当前功能启用`、`当前SAR与聊天输入` 加起来有 120 个维度。单看每一个都是
无害的枚举（头像是圆的还是方的、气泡用哪套样式、云端备份开没开），但**这么多维度组合
起来，对多数人是唯一的**。这意味着即使跨过月初、盐换了，理论上仍然可以靠这组设置把新旧
记录对上——也就是把 umami 原本一个月的关联窗口，延长成没有上限。

维度越多这个窗口越好接。加新维度前请先想清楚它能换来哪个具体决定，
换不来的就别加——这一节的数字也记得跟着改。

所以这两句话要分开说：

- **收集的内容里没有身份信息**：没有账号、没有 cookie、没有 IP 入库，没有任何一个字段
  来自你的对话、记忆、设定或输入。
- **但「无法关联到个人」不成立**：技术上做得到。我们不做，也没有任何代码在做，
  但这是靠承诺和可审计性保证的，不是靠技术上不可能。

所以这份文档和界面上都写「使用统计」，不写「匿名统计」——后者是个兑现不了的说法。

验证方式跟其他部分一样：代码全公开，数据库只有维护者能进，所有涉及数据的改动只能走公开 PR。
发现不对随时开 issue。

## 怎么自己核实

1. **读源码**。上面那张表，加上全仓库 grep `trackEvent`，就是全部。
2. **按 F12**，打开 Network 面板。前端跑在你自己的设备上，每个请求装了什么藏不住。
3. **看 PR**。所有涉及数据的改动只能走公开 PR。

## 加新埋点的规矩

节假日感知加入会话功能快照，仅上报「开 / 关」；国家、地区、时区、节日名称和日历数据均不上报。

真实定位加入 `当前功能启用` 的冷启动快照，只上报「开 / 关 / 读取失败」。不触发定位、不新增配置页点击或定位请求事件，不收坐标、地点名、隐藏地点名与半径、高德 Key、地图响应或失败原文。统计开关、DNT、本地开发和构建门禁照常生效。

1. 事件名用中文，跟用户在界面上看到的说法一致——按 F12 的人不用再对照一份英文 slug 表。
2. 属性**只能是固定枚举**，取值集合必须写死在代码里。任何来自用户输入或模型输出的字符串
   一律不许进去。
3. 遇到 dispatch 型的分发点（一处覆盖十几个子功能），**必须写显式白名单**。
   默认放行等于给未来挖坑：以后谁加一个新分支就自动被上报了。
   分发点的入参**不许原样透传**——命中白名单后重新写一遍字面量，
   免得哪天有人往那个入参里塞 URL 或报错原文。参考 `OSContext.showError`。

4. **崩溃 / 报错类事件只许上报「位置」和「类型代号」两样，且都必须是代码里写死的枚举。**

   ```ts
   // 对：类型由布尔谓词选出，值是写死的字面量
   trackEvent('触发 App 崩溃兜底页', {
       错误类型: isChunkLoadError(error) ? '资源加载失败' : '运行错误',
       所在App: INSTALLED_APPS.find(a => a.id === appId)?.name,
   });

   // 错：这些全都是运行时字符串，一律不许进上报
   trackEvent('崩了', { msg: error.message });        // 可能含用户数据、文件路径
   trackEvent('崩了', { stack: error.stack });        // 同上，还更长
   trackEvent('崩了', { kind: error.name });          // 看着像枚举，其实是运行时来的
   trackEvent('崩了', { kind: err.constructor.name }); // 同上
   ```

   **判断标准不是「有没有避开 .message」，是「这个值是不是我在源码里写死的」。**
   从异常对象上取的任何字段都不算，哪怕它平时只有几种取值。
   报错原文该去哪去哪——console、toast、给用户复制的剪贴板，就是不进 `trackEvent`。

5. **想加「某功能有多少人开了」的，加进 `utils/analyticsSnapshot.ts`，别在配置页现场发。**
   在配置页发只能逮到当场折腾的那批人，配好之后再没进去过的人永远不出现，
   拿这种数据判断「有没有人要这功能」会判反。

   收配置状态只许收「开没开 / 配了几个 / 用的哪家」，配置的内容一律不碰。
   服务商这类枚举要过白名单，认不出的收敛成 `custom`：

   ```ts
   // 对：布尔与档位，取值全是源码里写死的
   云端备份: triState(Boolean(cfg.webdavUrl?.trim()), cfg.enabled),
   云端备份服务商: enumOrCustom(cfg.provider, ['webdav', 'github'], '没配'),
   自配MCP服务器: bucketFewCount(servers.length),

   // 错：这些都是用户填的
   云端备份地址: cfg.webdavUrl,
   MCP服务器名: server.name,
   在用模型: apiConfig.model,
   ```

   加完在 `analyticsSnapshot.test.ts` 里给新字段的来源塞一个毒药串——
   那份测试会扫整份上报，漏收敛就会挂。

6. 改完在这份文档的事件清单里补一行。

### 当前功能启用

每次会话最多一次，五条快照轮流出场。回答的是「有多少人真的把某个功能配起来了」——这类功能配一次就长期
生效，只看「打开过配置页」那种事件的话，配好之后再没进过设置页的人永远不出现。

多数项报三个值：`开` / `配了没开` / `没配`。**「配了没开」单独占一格是有意的**：
那是试过之后放弃了，跟「压根没配」是两码事——前者说明引导在某一步劝退了人该修，
后者说明这功能没人要可以砍，混成一格就会做反决定。

- `当前功能启用` ——
  **外部服务接入**：天气（开/关）+ 自备 key（有/无）、热点（开/关）、真实定位（开/关/读取失败）、Notion、飞书、
  小红书、瑞幸点单、麦当劳点单、QQ 桥接；自配 MCP 服务器数 / 启用中的数 / 连通的数
  （都是 `0` `1` `2-3` `4+` 档位）、MCP 原生工具调用（开/关）。
  **数据与备份**：云端备份 + 服务商（`webdav` / `github`）、记忆向量模型、记忆副 LLM、
  记忆重排序、记忆云端同步、智能语境（`全开` / `部分开` / `全关`）。
  **协同工作**：是否用过、窗口数、消息数、文件数（后三项都只报 `0` / `1` / `2-3` / `4+` 档位）。
  **模型线路**：语音合成（`没配` / `minimax` / `fishaudio` / `elevenlabs`）、API 线路预设数（档位）、
  自习室独立线路、彼方独立线路。
  **推送**：主动消息 2.0（四态，见下）、开了 2.0 的角色数（档位）、
  即时对话（开/关，聊天主路径搬没搬上云端）、单独关了即时对话的角色数（档位）。

**主动消息 2.0 报的是四态，比别处多一档**：`没配` / `填了没连上` / `连上没开角色` / `开`。
它要连过三关才真的会响（填 Worker 地址 → 连接成功 → 至少给一个角色开），
而中间两种半途而废要修的地方完全不同——一个卡在那 15 分钟的部署流程里，
一个是后端弄好了但不知道还要去聊天里逐个角色打开。压成三态就分不出该修哪一段。

「开了 2.0 的角色数」数的是**角色级开关显式开着**（`activeMsg2Config.enabled === true`，
即 `isAmsg2EnabledForChar`）的角色。所有落盘路径（面板保存、工具桥建任务、认领自排任务）
都会显式写这个字段，所以「存过配置但没有 enabled」的悬空态不存在；从没碰过 2.0 的
角色自然不算——历史上曾用「没被关掉就算」的判定，那会把角色总数报成 2.0 用户数，
已在语义翻转（enabled 缺省从开改为关）时一并纠正。

「单独关了即时对话的角色数」数的是在角色的 2.0 面板里**显式关掉**即时对话
（`activeMsg2Config.instantChatEnabled === false`）的角色，分母是上面那格「开了 2.0 的角色」。
角色级开关缺省是「跟随全局」（字段不存在），所以这一格问的是「按角色区分这件事有没有人真用」——
长期是 0 的话，那个开关可以从角色面板收掉。

**这里只有开关和数量，没有一项是配置内容。** 地址、密钥、token、账号名、你给服务器
起的名字、城市名、数据库 ID 全部不碰；服务商这类枚举过白名单，认不出的一律 `custom`。
协同三项数量直接调用独立 IndexedDB 的 `count()`，不会读取窗口标题、协同消息、文件名或文件 Blob。

**模型名不报**，这不是漏了：那是你自己填的自由文本，撞「属性只能是固定枚举」那条规矩。
知道大家在用什么模型确实有价值，但按现在的规矩收不了。

**没报的**：主动消息 Push 加速——那一层已经全局下线（`proactivePushConfig.ts` 里的
`FORCE_DISABLED`），报出来恒定是「关」，看着像没人用，实际是被下掉了。
家园的独立线路是每个世界一份，按下面「没报的」同一条原则跳过。

**没报的**：每个世界一份（家园）、每局一份（跑团）的那些设置。一个用户能有十几个世界，
报哪个都不代表他；这些选择本来就有「选择世界时间模式」这类事件在记。

### 本次会话聊了多少

**发消息本身不打点**。那样服务端会攒出带时间戳的发送流水，
哪怕没有内容，「谁在几点连着发了多少条」也还原得出来。
这里只在页面切到后台时报一次区间，档位没变就不再报；一条没发过的会话一个点都不产生。

- `私聊会话发送条数` —— 0 / 1-10 / 11-50 / 51-200 / 200+

### 主动消息 2.0 · 送达端（只报失败）

配置成不成功是一回事，配完之后到点那条消息有没有真的出现是另一回事。后面这段全是
用户无感的失败——不报错、不提示，表现只是「角色今天没理我」或者「它说的话对不上最近发生的事」，
不主动收就永远不知道有多少人在这儿掉队。

**这几条只在失败时发，成功一个点都不产生。** 成功也报的话，服务端会攒出一份带时间戳的
「谁几点收到过角色消息」，那跟「发消息本身不打点」是同一条口径。

- `主动消息送达失败` —— `重试中` / `原文降级` / `被跳过`（本地存储故障时的三种处理）、
  `日程没落地`（角色改的日程没能应用）、`超时丢弃`（云端账本上有本该收到的消息，但超过
  两天的补收窗口，只能销账丢掉）。丢了几条不上报，这一格要的是「有没有人在丢消息」。
  每条另带 `stage`，标明是在哪一段挂的：`收发`（去重、认领任务、多段等齐这些环节的兜底）
  / `防穿帮闸` / `后处理` / `补收`。同一个 kind 有好几个发射点，光看次数不知道该查哪条路
- `2.0云端状态同步失败` —— 退避重试全打光还是没传上去，角色到点会带旧上下文说话。每次会话最多一次
- `2.0推送订阅自检失败` —— 订阅换了却登记不回 Worker，之后所有到点推送都石沉大海
- `即时对话发送失败` —— 这一轮没能交给云端（Worker 没受理），界面同一时刻已提示可重发
- `即时对话云端任务失败` —— 状态查询看到任务已失败 / 回复无法取回

每条都只有事件名和写死的代号，没有角色、没有内容、没有消息编号，失败原因（HTTP 状态、
上游报文）也不带。

「一键部署 2.0 后端」报 `成功` / `失败` / `要选账号` / `要起子域名` 四态。后两个不是失败，
是流程中途要用户补一个信息（token 能用在多个 Cloudflare 账号上、或者账号还没有
workers.dev 子域名）——分开报是为了看清有多少人卡在这两步上。Cloudflare 返回的报错原文
可能带账号 id 和 Worker 地址，只进界面和 console，一个字都不进上报。

「补装后端更新能力」是给老办法装的后端补一把更新用的钥匙，报 `成功` / `失败` /
`要选账号` / `要填Worker名` 四态。后两个同样是中途要用户补一个信息，不是失败。

「更新后端 Worker」是设置页那个让 Worker 自己取最新代码覆盖自己的按钮，报 `ok` / `failed` /
`unsupported` 三态；`unsupported` 是这台 Worker 还是旧版、没有自更新端点。

「暂停后台任务」是让 Worker 摘掉 / 加回自己的 cron trigger（暂停期间到点的主动消息和定时
消息先攒着，恢复后一起补发）。`action` 报 `pause` / `resume`，`result` 报 `ok` / `failed`。
旧版 Worker 没有这个端点时按钮整个不显示，所以没有「不支持」这一格；Cloudflare 返回的
报错原文只进界面，不进上报。

主动消息 2.0 的「连接并启用」「开启通知与推送订阅」「重置推送订阅」「深度重置推送订阅」
这几条报的不是成败两态，而是卡在哪一类：
`ok` / `success` / `地址没填` / `打到网页了` / `鉴权失败` / `端点不存在` / `建表失败` /
`配置缺失` / `网络失败` / `权限被拒` / `不支持推送` / `worker没配VAPID` / `订阅失败` /
`推送通道不通` / `没拿到订阅` / `端点僵尸` / `其他`。
其中 `配置缺失` 来自连接前那次 `GET /config-check`（worker 自己报缺 D1 绑定或 master key），
比 `建表失败` 精确——后者是按 HTTP 状态归的类，三种原因混在一格里。
`端点僵尸` 是重试到底浏览器还是只给 `permanently-removed.invalid`，设置页据此把
「重置订阅」升级成「深度重置」。
`推送通道不通` 是浏览器接口齐全、权限也给了，但 `subscribe()` 连不上推送服务商——
Chromium 系安卓版的网页推送要转交系统里的谷歌服务（GMS），没装 GMS 的国行安卓机全落这一格。
`没拿到订阅` 是它旁边那一格：`subscribe()` 既没抛错、也没给订阅，直接兑现成空（安卓 Firefox
上见过），浏览器一个错误对象都没给，所以只报事实、不猜原因。两格分开是为了看得出各占多少。
这几格跟 `订阅失败` 分开是因为要修的事完全不同：前者只能换浏览器 / 换网络 / 换设备，重试无用。
这些代号在**抛错那一刻**按 HTTP 状态和源码里的谓词挂上，报错原文（可能带 Worker 地址、
push endpoint）留在 toast 和 console 里，一个字都不进上报。

两条重置事件还带一个 `attempt`，是**分桶后**的连续失败次数（`0` / `1-2` / `3+`），
不是裸计数。

「刷新 Web Push 诊断」报的是设置页「推送订阅状态」面板当时的读数，全是固定枚举：
`permission`、`subscription`（`none` / `dead` / `active`）、`swState`（`activated` /
`none` / `other`）、`platform`（`normal` / `ios_needs_pwa` / `capacitor_native`）、
`registration`（`worker-unset` / `unreachable` / `missing` / `other-endpoint` / `matched`）、
`lastFailure`（`none` / `channel-unreachable` / `unsupported` / `permission` / `state` /
`zombie` / `unknown`）、`delivery`（`clean` / `gone` / `recovered` / `unknown`）。
`registration` 是「worker 上登记的订阅是不是这台设备」，中间那两档对应的是任务建得成、
到点却一条都不来的静默失联。
`delivery` 是上一次推送有没有被推送服务退回，结论由 Worker 那侧算好（`/debug` 的
`pushDelivery`）。`gone` 指现在这条订阅在推送服务那侧已经作废（登记状态可能全对，推过去
只换回一个 410），`recovered` 指出过这事但之后订阅换过一条了，`unknown` 是没问到——
没连上 Worker、这台 Worker 上跑的后端还不查这一项、或者它查了没查成，三种都归这一格。
`gone` 那一格量大说明「全绿但一条不来」正在成批发生；`unknown` 常年居高则说明大批用户
的 Worker 还停在老版本上。
`lastFailure` 是最近一次建订阅失败卡在哪类，手上已有活订阅时报 `none`。
`channel-unreachable` 那一格量大就说明有一批设备（多半是没装谷歌服务的国行安卓机）
从系统层面就用不了网页推送——这是它唯一能被看见的地方。
端点地址、Worker 地址、报错原文一概不带。

「探测 2.0 Worker 能力」每次会话最多一次，报 `ok` / `版本过旧` / `缺特性` / `端点不存在` /
`探测失败`。跑着旧 worker 的表现是静默错（自述回写不落盘、任务重复推），用户不会来报，
这条是唯一能看见的出口。

「即时对话能不能开」每次会话最多一次（打开面板、探测完成后），只在填了 Worker 地址时报。
`result` 是三道门里最先没过的那一道：`可以开` / `没连上Worker` / `没开推送` / `Worker太旧`；
`state` 是这个人当时开着没：`已开着` / `还没开`。
开关灰着的时候用户什么都点不动、也就不会产生别的事件——不收这一格的话，被挡在门外的人
和「不想要这功能的人」在数据里长得一模一样。已经开着的人也报，是为了看见另一种坏法：
开的时候好好的，后来 Worker 退回了旧版，于是发一条挂一条而设置页还写着「已开启」。
三道门的判定跟界面上那行黄字共用同一个函数（`utils/amsgDiagnostics.ts`），
上报和提示不会各说各话。

「切换即时对话」报 `开` / `关`。配置快照里那一格只看得到「此刻开着没」，
开了之后又关掉的人在那儿跟从没开过的人是同一个样子，而这两种要修的东西完全不同。

### 3D 家园与居家桌面

- `进入3D家园`：场景已就绪且未挂起时，每次挂载一次；入口仅「小屋 / 居家桌面」。
- `打开3D家园功能`：当面聊天、日常记录、家园设置、人物互动、小手机、手机聊天、拍照、布置房屋、房间分享、3D形象、宠物。只计打开入口，不逐条统计聊天、自动活动、动作帧或触摸。
- `3D家园数据操作`：成功发起下载整屋备份、恢复整屋备份、下载房间布局、复制房间布局、应用房间布局。下载只表示交给浏览器，无法获知用户是否最终保存文件；取消或解析失败不计成功。
- 外观快照增加 `居家配色`（apricot / blue / rose / lilac / oat / custom / 未使用）与 `居家锁定角色`（开 / 关 / 未使用）；桌面皮肤按内置白名单收敛。
- 角色设置快照增加 `3D家园角色数`，沿用 `bucketFewCount` 的计数档位。为保持快照宽度预算，不逐项增加自主活动、说话及形象配置属性。

入口封装为 `utils/homeAnalytics.ts`，最终仍走 `trackEvent` 的开关、DNT、构建及局域网门禁。未知输入直接丢弃。不会上传角色/宠物名称、ID、聊天、日常记录、秘密、房间名、上传文件、贴图或颜色值。回归覆盖毒药字符串，功能收集不读取图片或秘密存档。
