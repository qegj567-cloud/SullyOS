# 性能约定：只读用得到的数据

重度用户的单个角色有上万条聊天、几百条记忆，本地存储几百 MB。把一个角色的消息整段读出来，在中端手机上要几百毫秒到一秒；这类开销一旦挂在「每次启动」「每次回复」「每隔几秒」上，就是日常卡顿和发热的来源。这份文档记录各条热路径上现在的读法和它的边界，改到这些地方前先看对应小节。

通用原则：

- 热路径上只读最终会用到的那一段，用按主键范围、按索引倒序的接口，不整表 `getAll()` 再切片。
- 高频变化的状态（播放进度、流式文本）不让大组件订阅；需要时在用的那一刻读快照，或者合并成固定节奏更新。
- 「少读」必须和「读全量」得出同样的结果。做不到等价的地方保留全量，并写明原因。

## 启动

| 做法 | 位置 | 边界 |
|---|---|---|
| 启动只读桌面外观用到的资源：壁纸、锁屏壁纸、自定义字体、图标、小组件、外观预设、桌面装饰 | `DB.getStartupAssets`（`utils/db.ts`），调用点在 `context/OSContext.tsx` 的设置装载段 | assets 表里还有语音、语音合成缓存、歌曲缓存等大块数据。启动逻辑要读新的键时，先在 `getStartupAssets` 的键名或前缀清单里登记，否则读不到。`utils/db.startupAssets.test.ts` 钉住每一类都读得到、语音缓存读不出来 |
| 记忆向量的开机扫描在完整扫完一轮后 7 天内不重复 | `MemoryVectorDB.scanAndMigrateLegacyIfNeeded`（`utils/memoryPalace/db.ts`） | 记录按用户空间各一份，存在 localStorage，属于设备状态不进备份。恢复或导入开始写库时调 `invalidateVectorCompactScan()`，所有空间的记录一并作废；扫描中途失败或撞上恢复不留记录。「优化资源存储」的手动扫描不看这条记录。不要把「本轮迁移了 0 条」当成「没有旧格式数据」去跳过更多 |

## 常驻开销

| 做法 | 位置 | 边界 |
|---|---|---|
| 定时消息轮询每 5 秒先用一次查询找出有到期消息的角色，没有就结束 | `DB.getCharIdsWithDueScheduledMessages`，轮询在 `context/OSContext.tsx` | 定时器只依赖「有没有角色」，角色列表每轮从 ref 现取；让 effect 依赖整个角色数组的话，任何角色字段更新都会重建定时器并立刻全查一遍。到期判断、压着不投的条件和投递顺序在逐角色那段里，没有变 |
| 只需要一个角色的最新数据时用 `DB.getCharacter(id)` | `context/OSContext.tsx` 的三处事件回灌 | 角色对象内嵌全部记忆、手机状态等，整表读出再 `find` 的代价随角色数增长 |
| 聊天页不订阅音乐上下文 | `hooks/useChatAI.ts` 在 `triggerAI` 入口读 `loadMusicPlaybackSnapshot()` | 播放进度每秒更新约 4 次，订阅整个上下文会让聊天页跟着重渲染。快照在发送那一刻读，读取时机不要前移：模型看到的歌要和那一刻展示的一致。音乐动作走 `loadMusicHooks()`，不依赖订阅 |

## 聊天回复

三个纯函数在 `utils/chatPerfHelpers.ts`，测试在同名 `.test.ts`。

| 做法 | 边界 |
|---|---|
| 生成途中每落一条气泡，刷新界面只读界面画得出来的那一截（可见条数 + 16） | `readChatRefreshTail`。可见消息不够画满，或流式预览交接时读回来的那一截够不到本轮开头，就退回读 200 条。旧消息定位模式照旧读 200 条。要把读到的列表交给 `triggerAI` 的两处（`apps/Chat.tsx`）和记忆宫殿、主动消息运行时的读取没有改 |
| 流式预览每 60ms 至多更新一次 | `createCoalescedRunner`。网络包到达时只记下最新全文；进入落库后处理前同步补算最后一次，尾巴不依赖定时器。用 `setTimeout` 而不是 `requestAnimationFrame`，页面在后台时后者不触发。用户点停止时保存的是已经上屏的内容。思考与正文的分流规则见 [`thinking-response.md`](./thinking-response.md)，合并只改节奏不改分流 |
| 语音回填对每条消息在一次停留期间最多查一次库 | `pickVoiceHydrationTargets`。查过没有语音的消息记账，换角色清空。新语音唯一的写入口 `saveMessageVoiceIfCurrent` 会直接更新界面并把那条消息从记账里拿掉；以后新增别的语音写入路径时要做同样的事，否则语音合成完了语音条不出现 |

## 提示词与记忆整理

| 做法 | 位置 | 边界 |
|---|---|---|
| 私聊提示词里的群聊背景，每个群只读最后 `cap` 条 | `utils/chatPrompts.ts` | 群消息按 id 排列，归档线也是 id 门槛，所以「取尾部再过滤归档线」和「过滤再取尾部」是同一批消息。`cap` 不是正整数时照旧读整群 |
| 记忆整理的日常路径只读水位线及之后的私聊消息，不够「热区 + 1」条时往前补 | `loadSemanticMessageTail`（`utils/memoryPalace/pipeline.ts`） | 缓冲区只取水位线之后、热区之前的消息，热区起点是倒数第 N 条，两者都落在这段尾部里，结论与读全量相同。`force` 和一键存入的边界按全部原文计算，保持全量读取。水位线为 0 或长期不前进时，尾段就是全量。`pipelineDailyRead.test.ts` 用全量读法现算对照值 |

## 怎么量

用假模型（[`fake-llm.md`](./fake-llm.md)）加灌进 IndexedDB 的几千条消息，在页面里给 `IDBIndex.prototype.openCursor`、`getAll` 和 `IDBObjectStore.prototype.get` 套一层计数，再发一条消息、触发一次回复，比较改动前后各张表被读了多少行。2026-11-27 的一次对照（3000 条历史、5 条气泡的流式回复、点击回复后 8.4 秒内）：读出的消息行数 2053 降到 1283，查语音的次数 537 降到 25，流式期间聊天区的 DOM 更新批次 141 降到 37。这组数字来自桌面浏览器和很短的测试消息，只用来确认方向，不代表手机上的绝对耗时。
