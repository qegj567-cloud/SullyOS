# 主动消息 2.0 总纲

主动消息 2.0（代码里叫 amsg2）让角色在 App 关着、手机锁屏时也能来找用户。用户在自己的 Cloudflare 账号里装一台 Worker 和一个 D1 数据库，即时对话、定时主动消息和后台整理都在这台 Worker 上跑，结果通过 Web Push 推回手机。

这份文档放三样东西：设计目标、红线和通用教训。各子功能的细节放在各自的文档里，入口见文末的「文档导航」。改主动消息 2.0 的任何部分之前，先把这一份读完。

## 设计目标

1. **页面关着也要来。** 生成交给云端以后，客户端就不用再守着请求了。一件事值不值得搬上云，看「生成要多久 × 这段时间用户离开的概率」：用户大概率还在场、几秒就生成完的，留在本地。
2. **即时对话是聊天的主路径。** 按发送只发一个很小的请求，生成在用户自己的 Worker 上跑，结果用推送送回来。发出去之后客户端就不用管了，模型慢不算失败。体感接近真人回消息，但也不假装秒回。
3. **后端是用户自己的，搭起来零门槛。** 全程在网页上点完，只要一枚 CF Token。本地数据是唯一的真相，云端只存跑任务需要的增量。
4. **用户说了算。** 频率和额度由用户定，角色只能在上限之内挑时机。不替用户删任务，不替用户打开 2.0。总开关关掉时保留配置，就地暂停。
5. **云端生成跟本地生成是同一个角色。** 角色设定、世界书、记忆召回、聊天上下文在两边要一致，差异只能是有意设计的。具体规则见下面「云端与本地一致」。

## 红线

每条红线后面写了它在哪里被拦住（代码闸或测试）。没写的，靠评审把关。

### 云端与本地一致

- 云端拼出来的提示词和上下文，跟前端本地生成相比，只允许有**登记过、有明确决定和理由**的差异。没登记的差异一律按 bug 处理，不管它看起来多无害。
- 新发现差异时先报告，由维护者决定这个能力是搬上云、还是在云端去掉以和本地对齐，决定之后再登进下表。不能自己判断「这点差别无所谓」就放过。
- 最容易出事的是「丢东西」：本地会带、云端漏带。记忆召回出过一次这种事故，本地私聊顺带完成的召回，云端快照里没有。新增拼角色上下文的入口必须自己带召回，由 `utils/contextPipeline.test.ts` 的静态检查拦住。

已登记的有意差异：

| 差异 | 云端的做法 | 理由 |
|---|---|---|
| 实时信息（天气、热搜、节日） | Worker 每次现取，常驻注入；取不到就整段不出现 | 页面关着时本地拿不到实时数据。节日跟随聊天时间感知开关 |
| 排程能力说明 | 提示词里告诉角色能排什么、受哪些上限约束 | 只有云端能在页面关着时按时发出 |

> 这张表还没逐项核对完，云端和本地之间可能还有没登记的差异，核对时按上面的规则处理。

### 回退本地

- 即时对话失败不自动重试，也不悄悄转回本地生成。
- 用户自己没开 2.0 时（总开关关着、没填 Worker 地址），本地生成本来就是用户的选择，直接走本地。
- 云端跑不了这一轮时可以转本地，但界面必须标明「本机生成」，并留下 trace。代码里认的情况在 `utils/amsgInstantChat.ts` 的 `resolveInstantChatReadiness` 和 `hooks/useChatAI.ts`，目前有这几种：
  - Worker 太旧，或者绑定没接上（`worker-outdated`）；
  - 这一刻连不上 Worker（`worker-unreachable`）；
  - 这一轮用到了只能在本机跑的东西：瑞幸 / 麦当劳小程序、所在 Worker 连不上的 MCP、遇到旧 Worker 或没探到版本的 SAR 模块。
- 新增转本地的情况要登记到上面这张清单，并且同样要标明、要留 trace。没登记的回退按 bug 处理。

### 凭据与隐私

- 凭据在云端加密存储，查询接口永远不返回明文。凭据不进推送、不进收件箱、不进日志，也不写回任务行。
- 用户亲手保存 API（设置页保存或切换预设、2.0 设置里保存任务、改角色独立 API、在云端恢复角色）时，直接用本机配置覆盖云端，不信本机记的「上次传过什么」那本账。那本账只记录本机传过什么，云端那一份可能已经被别的入口改过（Safari 和主屏 App 的存储是分开的，或者换过 Worker）。只有启动时的自动补传还按账判断，免得每次打开都多发一次请求。由 `utils/amsgStateSync.test.ts` 钉住。
- CF Token 只放在页面内存里。连接码里不带 Token、API Key 和聊天内容。
- 后台 MCP 的流量不经过项目方服务器。中转不记路径、目标 Worker 和 IP；开启中转前要讲清楚中转能看到全部内容。

### 频率与费用

- 上限靠代码里的硬闸拦住，不靠提示词去劝。默认值只在 `utils/amsgLimits.ts` 定义一次：连发 3 次、最短间隔 10 分钟、重复任务连续 3 次没回就停、同时最多 5 个任务（用户可调 1~10）。角色自己排的循环任务和「到点必发」默认关闭。
- 主动消息按「次」计数，「条」只用来数气泡。即时对话的回复不计入。
- 连发上限只有在用户开口说话后才清零。
- 离开后消息到点必发，计入连发上限，一次离开只找一次。见面离开提醒不受连发和每日上限限制，也不给角色排程工具。各自的理由见对应文档。

### 推送

- 推了就一定弹出来。不想弹的内容压根不推，只进收件箱。iOS 上「推了但不弹」会耗掉静默推送配额，攒多了系统会吊销订阅。
- 一个用户只有一个推送订阅，界面不能宣称多台设备会同时收到。
- 推送不是数据同步通道。后台产生的副作用等客户端上线后去拉。

### 数据与删除

- 只有用户亲手发起的操作才会真删：重置、删角色、点清理按钮。推断出来的失效（换了 Worker 地址、角色成了孤儿）一律只提示、留线索，不动手。
- 云端有哪些数据，以云端实际存储为准。删除失败不能报成功。
- 即时对话的输入在这一轮结束后立刻删除，7 天过期只是兜底，处理删除失败或这一轮一直没结束的情况。

### 部署与版本

- Worker 和前端都要改时，先部署 Worker。改了 `worker/amsg/src` 用到的代码，必须重打 bundle 并提交，需要用户更新的改动要推进 `utils/amsgBundleVersion.ts`（有守卫测试）。
- 前端出错的根因是 Worker 版本旧、前后端不一致时，去部署 Worker，不在前端加兜底来掩盖。
- 判断 Worker 支不支持某个功能，只在一个地方做：读体检接口 `/config-check`，不在每次调用前单独去问 Worker。即时对话能不能跑，看运行时有没有接上起跳器绑定（`instantTick`）；bundle 版本只用来决定要不要提示更新，以及需要新协议的那一轮能不能上云。之所以要分开看，是因为自更新时跑的是旧代码，版本号已经新了，绑定却可能还没接上。
- 没发布的功能不做旧数据兼容。真实运行时会遇到的情况照样要防：网络重试、浏览器差异、数据损坏。
- 新增 Worker 接口时同步中转的路径白名单，有测试对照实际路由。
- master 上的 Worker 改动等于已经发布：用户的 Worker 会按 bundle 指纹自动跟上 master。

### 架构边界

- CF 的 `ctx.waitUntil` 最多 30 秒（从响应发出或客户端断开时开始算）。后台生成一律走 Durable Object 的定时器或 cron，不能依赖 `waitUntil`。
- 进 Worker bundle 的公用模块不能引入浏览器依赖。

## 通用教训

这几类错误都犯过不止一次。

1. **部署顺序和 bundle。** 「Worker 先部署」「bundle 忘了重打」是最常见的事故来源。动 fire_pack 版本、加表、加绑定、改共享键格式之前，先想好部署顺序。
2. **重构时断了隐式依赖。** 搬一条流程时，要把它顺带完成的事一起列出来：换了「怎么查」，就要检查「什么时候查」还在不在；召回原来是在别的流程里顺带完成的，那条流程一改就断了。
3. **静默失败。** 表结构漂移、推送订阅已经作废、分流被否决，这些情况下体检全绿，功能却不工作。每次跳过、否决、降级都要留下看得见的痕迹。
4. **先查证再下结论。** 线上问题先拿埋点、云端数据和用户的 CF token 实测坐实，再判断是谁的问题，不要先怪用户配置或最近的升级。

## 平台硬限制速查

| 平台 | 限制 |
|---|---|
| CF Workers | `waitUntil` 墙钟 30 秒，付费版也一样；自更新时第一次跑的是旧代码，新加的绑定要第二次才生效 |
| D1 | LIKE 匹配串最多 50 字节；单条语句最多 100 个绑定参数；每日 500 万读的是行数，不是查询次数；本地 SQLite 复现不了这些，测试要断言 SQL 的形态 |
| D1 | `CREATE TABLE IF NOT EXISTS` 不会给已有的表补列。Worker 每次升级都要跑一遍 schema 检查 |
| Web Push | 推送明文上限 3993 字节；订阅在推送服务那边作废时返回 410，要当成终态处理 |
| iOS | 前台收到推送却不弹，会消耗静默推送配额；没有 tag 却带 `renotify` 会抛错 |
| GitHub raw | CDN 缓存 5 分钟，绕不过去；自动更新检查的间隔不低于 30 分钟 |
