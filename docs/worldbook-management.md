# 世界书编辑、分组与角色挂载

2026-09-13 修复。

## 用户操作

世界书按「外层分组 → 整本世界书（`category`）→ 词条」三层组织：

- 顶部「分组」可将多本世界书归入同一个外层分组（字段 `group`），未归入任何分组的世界书显示在「未分组」；尚未创建外层分组时直接平铺展示各本世界书。「编辑分组」可重命名或增减组内世界书，「解散」只把组内世界书退回未分组，保留全部内容与角色挂载。
- 分组标题行带整组总开关：组内任一本世界书开启时点一下可把整组世界书一并停用；全关时点一下一并开启。组内每本世界书标题行也带独立的整书开关（字段 `bookDisabled`），可在组内单独启停某一本世界书；展开后每条词条右侧也可直接切换单条开关（字段 `disable`）。
- 整本书开关（`bookDisabled`）与词条自身开关（`disable`）独立保存：关闭再重新开启整本世界书或整个分组时，书内原本由作者停用的分割线说明或互斥分支保持停用状态。往已有世界书新增或导入词条时，沿用该书当前的外层分组与整书开关状态。

世界书 App 导出的 JSON 使用 `format: "sullyos-worldbook"`、`version: 1` 和 `worldbook.entries`。导入同时接受条目位于顶层 `entries` 的旧版和酒馆世界书。新版往返保留本机条目标题和导入条目的注释语义。单本世界书导出 JSON 与角色卡分享仅保留词条自身的 `disable`，不携带本机外层分组名 `group` 和整书静音状态 `bookDisabled`（避免暴露私人分组归类或导致接收方导入后整本书默认失效）；整机备份、单用户备份与用户空间迁移完整保留两者。格式标记说明导出软件，作者和设备身份无法从中推断。

- 关闭「关键词触发」改为常驻时，主关键词、辅助关键词仍然保存；重新启用即可继续使用。
- 每本世界书下方可「编辑整本」：改世界书名称、调整所属外层分组、保持原触发方式、全部常驻或全部关键词触发。任一条缺少主要关键词时，整本关键词切换不执行，提示先补齐。停用状态和其它匹配规则不变。
- 改名不允许与已有世界书合并，避免意外混书。世界书名称和外层分组名称都是归类字段，不是绑定标识。
- 「删除整本」会显示词条数量并确认，同时从已挂载的角色中移除这些词条。取消不更改数据。多选删除使用同一批量通道。
- 神经链接的扩展设定按已挂载的世界书折叠，同时标出所属外层分组与「世界书已停用」提示；挂载弹窗在建有外层分组时支持「挂载全组」或单本「挂载整本」。展开后点击词条才挂入正文；「整组取消挂载」只修改当前角色，不删公共库、不影响其他角色。

旧版本若已把关键词清空并保存，不能从现有数据推算回来。应从原文件补回原条目的关键词；不要通过替换条目 ID 自动重建绑定。

协同工作的「世界书制作」也生成糯米机 v1 作品。作品额外带安装分组名 category，预览与安装共用世界书读取逻辑。历史协同作品的顶层 entries 和早期单条目仍能打开。

## 绑定不变量

绑定只按条目 `id`，从不按标题、分组名或导入的 `sourceUid` 匹配。

`DB.mutateWorldbooks` 在同一个 IndexedDB 读写事务内读取最新库记录、修改目标条目、同步角色的 `mountedWorldbooks` 缓存；事务提交后才刷新 OSContext。批量操作不能循环使用捕获了旧 `characters` 的单条更新函数，否则后一次保存可能复活前一次已删除的挂载，或覆盖前一次同步。

- 修改保留原有 ID、创建时间和挂载顺序；只更新已绑定该 ID 的角色，不新增挂载。
- 部分挂载继续保持部分挂载；角色卡自带、公共库没有的其它条目保留。
- 删除按显式选中的 ID 集合执行，不按同名分类删除角色自带条目。
- 世界书库与缓存任何一步失败，全事务回滚。已修改角色在提交后标记云端提示词待刷新。

## 启用场景

每条世界书可以限定只在某些生成场景里生效。默认是全部场景；旧数据、导入的酒馆世界书、协同工作装上的作品，没设过的都按全部场景处理。

适合的用法：一组只给跑团用的规则书，编辑整组 →「整组启用场景」选「统一设为…」→ 顶部「全选关」→ 展开「其他 App 玩法」只打开「跑团」。这样私聊、主动消息和记忆总结都不会带上这组条目。只想在线上场合用的人设补充，可以关掉「线下在场」整类。

### 界面

条目编辑页「启用条目」下方是「启用场景」，收起时显示摘要（全部场景、具体分类名、已选几个场景或「仅应用内勾选时生效」）。展开后分六类：线上私聊、角色主动找你、多人、线下在场、其他 App 玩法、记忆与整理。每类可以整类开关，也可以展开逐个 App / 功能开关；顶部和每类都有「全选开」「全选关」。列表里限定过场景的条目带「限定场景」标记，一个开关都没开的带「未启用场景」，这时只有见面·剧情这类在应用里手动勾选了才会用到。

「编辑整组」的「整组启用场景」可以保持各条原设置，或把整组统一设成同一套场景。

几个场景没有独立开关：

- QQ 桥、存钱罐、手账这几个 App 目前不对用户开放，界面上不单列，合在所属分类末尾的一个「其他」开关里，一起开关。
- 见面·剧情只列出、不给开关，提示「请在对应应用内勾选调整」。这个 App 在每条剧情的「世界书沙盒」里勾选用哪些书，场景筛选对它不生效。

### 判定规则

场景是额外的「并且」条件：条目要先在当前场景里允许，再按常驻 / 关键词 / 概率判断。不在当前场景的条目在关键词扫描和概率抽签之前就被拿掉，不会占掉一次概率抽签。

条目上存的是 `scenes` 字段，值是场景令牌列表，定义和判定都在 [`utils/worldbookScenes.ts`](../utils/worldbookScenes.ts)：

| 值 | 含义 |
|----|------|
| 不存在 / `null` | 全部场景（默认） |
| `[]` | 哪里都不生效 |
| 分类 id，如 `apps` | 整个分类，包括以后新加进这个分类的场景 |
| 子场景 id，如 `apps.trpg` | 只这一个场景 |
| 认不出的令牌 | 判定时忽略；编辑开关时原样保留 |

界面写回时会自动收拢：一个分类要求的子场景（包括「其他」里的隐藏场景）全开，就写成分类令牌；所有分类都开，就写回「不存在」。

分类的全开 / 部分 / 全关状态和摘要都按界面上的行来算，「其他」算一行，它管的几个场景全开才算开着。见面·剧情不给开关，不计入。

### 为什么这样设计

- 分类令牌覆盖以后新增的场景。整类打开的意思是「这一类都要」，以后在这一类里加新 App 时不需要用户回头再开一次；只开了某几个子场景的条目则不会被新场景顺带打开。
- 顶层「全选开」写回「全部场景」，不写成一长串令牌。这样它和从没设过的条目是同一个状态，以后新增分类也会包括进去。
- 隐藏场景（`hidden`）用的人少，不值得逐个列出，但判定时实打实生效。所以它们合成一行「其他」，并且计入分类状态和摘要：如果完全不显示，就会出现分类显示全开、QQ 桥里却不生效的情况。收拢时它们也算在分类要求的子场景里。
- 摘要不写「哪里都不生效」：见面·剧情不受场景开关控制，在应用里勾选过的书照样会用到。
- 记忆总结与归档、用户印象、写作风格分析、记忆宫殿整理单独成「记忆与整理」一类。这些后台任务同样会读角色挂载的世界书，不单独分类的话，限定在某个 App 的书会漏进记忆总结，把玩法里的设定写成长期记忆。
- 见面·剧情由 App 自己管理。它已经按每条剧情勾选具体的书，再叠一层场景开关会出现两处设置互相打架、用户不知道该改哪边。
- 认不出的令牌保留。新版本写入的场景被旧版本打开编辑时不会被丢掉。
- 导入世界书文件和角色卡时都会清洗 `scenes`（`sanitizeWorldbookScenes`）：不是数组按全部场景，元素只留字符串。别人给的文件里这个字段写坏了，也不会让这个角色以后每次生成都报错。

### 生成管线

所有生成入口都要声明自己是哪个场景。ContextBuilder 在解析世界书的唯一入口按场景筛选（[`utils/context.ts`](../utils/context.ts)），对象参数入口靠类型必填，位置参数入口和写死的场景字符串由 `utils/contextPipeline.test.ts` 的静态检查兜住：漏写场景、写了没登记的场景都会让测试失败。

新加 App 时：

1. 在 `utils/worldbookScenes.ts` 的 `WORLDBOOK_SCENE_CATEGORIES` 里给对应分类加一个子场景（id 用 `分类.名字`，`label` 是界面显示名）。界面上不想单列的加 `hidden`；App 自己挑书的加 `appManaged`。
2. 生成请求经 `ContextBuilder.buildCharacterRequest` 等入口时传这个场景。
3. 跑 `utils/contextPipeline.test.ts` 和 `utils/worldbookScenes.test.ts`。

加进已有分类后，整类打开的条目会自动包含新场景，只开了部分子场景的条目不包含。

### 主动消息

定时主动消息、角色自己约的下一条、离开后消息、见面离开提醒共用同一份 fire_pack 模板。只在其中几种里生效的条目沿用概率条目已有的标记随包携带，另附允许的种类列表，Worker 到点时按这次的种类去掉不允许的条目。本机生成离开后消息和见面离开提醒时已经知道种类，打包时直接按种类筛掉，输出和 Worker 逐字一致（`utils/awayMessage.parity.test.ts`）。种类和场景的对应只写在 `utils/worldbook.ts` 的 `AMSG_PROACTIVE_KIND_SCENES` 一处，Worker 也从这里取。

旧 Worker 不认识这份种类列表，会在四种里都带上这些条目。这是接受的退路：主动消息里多一条设定的代价，比该有的设定缺席小；更新 Worker 后就按种类筛。

### 导出与备份

糯米机格式导出只在条目设过场景时写 `scenes`，没设的条目不带这个字段。酒馆格式不带场景，导入的酒馆文件都是全部场景。整份备份和云备份按记录原样保存，场景自动随行。

协同工作的世界书制作器不在提示词里教模型写 `scenes`，场景交给用户装好后在界面里调。糯米机 v1 作品里如果带了 `scenes` 数组，预览、校验和安装都会保留，并同步进挂载缓存；字段缺失、不是数组或作品是酒馆格式，就按全部场景安装。历史协同作品照常打开。验证：`utils/collaborationMakers.test.ts`。

## 全 App 世界书构建管线

新 App 的默认入口是 `await ContextBuilder.buildCharacterRequest({ char, user }, messages)`，返回可直接发送的完整消息数组。角色档案、挂载世界书、固定位置和指定深度一次装配；不要先拼 `buildCoreContext` 再调用它，否则会重复人设。App 只负责本次玩法规则、输出格式和本场景历史。

`buildCharacterContext({ char, user, history, instructions })` 是需要拆分主提示词与历史的同一管线接口（聊天、见面、通话使用）。`buildWorldbookRequest` 服务剧场的自定义预设布局，`buildGroupWorldbookRequest` 服务多人布局；这些都在 ContextBuilder 内调用同一解析器和深度放置器。App 不得直接调用世界书解析/插入函数。

### 顺序和深度

- 固定位置优先于 order；同一位置/深度按 order 升序，同序保留挂载顺序。
- 深度按本次实际发送的历史消息从末尾倒数，包含本轮用户消息；0 在末条之后，超长深度钳到历史开头。世界书和额外系统规则不参与计数。无历史时也保留独立角色消息。
- scanDepth 只决定关键词扫描范围，与注入 depth 无关。常驻、禁用、关键词、辅助关键词、概率和宏替换都在公共层处理，概率同轮只抽一次。
- system/user/assistant 由条目 role 决定，不把所有深度条目压成 system 文本。
- 历史必须先按场景范围筛选、转成实际请求消息。不要为触发世界书读取隐藏/归档对话；空范围不能回退全库。App 的系统规则默认不参加关键词扫描。
- 群聊同 ID 只激活一次，同时保留条目所有者；私有条目不能作为所有成员共同设定。剧场仍使用场景选中的书、预设启用状态与角色归属，深度插入不会计入预填充。

参考 [SillyTavern World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/) 的基础语义。这里没有实现酒馆全部递归、预算、Outlet 等高级功能，不宣称完整兼容。

### 已接入与兼容边界

聊天、见面发送/重生成/开场感知、通话、群聊、剧场、跑团、Spark、学习、日程、交换日记、歌词本、攻略本、小说、都市人生、角色间私聊、自由活动、记忆潜行、触碰/陪伴、节日活动等生成入口使用消息管线。单次生成只有一条任务消息时，深度 4 会自然落在该消息之前；不会把任务正文中的换行冒充四条历史。

旧 `buildCoreContext` 只用于文本兼容：全部已激活位置都有正文，但字符串无法携带消息角色和真实深度。保留的消费者是记忆诊断/迁移/门牌任务，以及多人布局的无世界书人设子块。旧主动消息模板也仍是单串协议：包含激活条目正文，但不保证独立消息角色/深度；不能将此称为消息模式。当前前台聊天请求不走这个降级接口。

新增 App 必须使用消息入口，不再新增文本兼容调用。`utils/contextPipeline.test.ts` 限制旧入口扩散和 App 私自解析世界书，`utils/contextWorldbook.test.ts` 验证公共行为。后续若调整旧后台模板协议，应连同 Worker 契约与对应测试迁移，不能仅改文本拼接。

### 笔友会写作人格

「深度分析写作风格」使用 `buildCharacterRequest`，携带角色核心设定、当前挂载且满足触发条件的世界书、用户档案及按公共规则可读的记忆。分析规则放在系统指令中，不参与世界书关键词扫描；指定深度和消息角色由公共管线保持。

`CharacterProfile.impression` 是角色对 **用户** 的印象，不是角色自己的性格档案。笔友会不得把其中的 MBTI、特质、喜恶、习惯、总结拿来充当作者人格、写作禁忌、范文或采样参数。世界书绑定给角色也不代表条目里每个人物都属于角色；分析和共创提示词明确区分 char、user 和小说人物，用户资料仅用于互动关系。

未生成创作档案时使用中性占位与通用写作指导，不从备注、混合世界观或用户印象猜出固定性格。保存的 `writerPersona`（包括手工修改）原样保留；旧分析如已混淆，需要用户点「深度分析写作风格」重新生成或手动修正。请求失败或输出为空不会覆盖旧档案，也不会以本地兜底冒充分析成功。

验证：`utils/novelPersona.test.ts`。

### 发送统计

统计按正文标题拆分；沿用 master 的修复，世界书条目内部小标题不再拆散世界书分区。`apiCallLog.findBlockHeaders` 通过 `formatWorldbookSection` 的收尾格式（条目末尾 `---`，整段末尾额外空行）识别边界，修改格式须同步统计解析与测试。完整请求 JSON 用于确认实际发送内容。见面用户输入参与关键词匹配，VN 指令不参与；depth=0 条目不会被错误追加用户输入的 System Note。

验证：`utils/contextPipeline.test.ts`、`utils/contextWorldbook.test.ts`、`utils/chatRequestPayload.test.ts`、`utils/datePrompts.test.ts`、`utils/worldbook.test.ts`、`utils/storyTheater.test.ts`、`utils/apiCallLog.test.ts`。

视频通话先给真实用户消息贴摄像头快照，再构建世界书消息；不支持图片时只还原原用户消息，保留同轮世界书的激活结果与顺序。群聊输出继续沿用 master 的思考块清理逻辑。


### 3D 实验分支对齐（2026-10-05）
